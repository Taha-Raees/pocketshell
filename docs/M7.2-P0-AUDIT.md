# M7.2 P0 — Architecture Audit: Sessions, Processes, Agents, Notifications

**Status:** P0 audit + design. No M7.2 production code exists yet.
**Baseline audited:** HEAD `d4cf363`, working tree clean, versionCode 47 /
`0.11.2-m7.1.1` (the M7.1.1 fix release, tag `M7.1.1-fix`).
**Method:** every claim below cites the real symbol/file it was verified
against in this tree. Nothing is assumed from upstream Termux behavior,
documentation, or other Android terminals; where the architecture cannot
know something, this document says so explicitly.

The one question this audit answers:

> **What can PocketShell actually know about a running terminal, process,
> session, and AI agent — and where does that information come from?**

---

## 1. PART A — The real session architecture

PocketShell has **two separate process domains**:

1. **PTY sessions** (the terminal) — `app.pocketshell.terminal.*` on top of
   the vendored Termux emulator (`com.termux.terminal`, module
   `terminal-emulator`, JNI in `terminal-emulator/src/main/jni/termux.c`).
2. **Package operations** (apk update/search/install/probes) —
   `app.pocketshell.packages.GuestCommandRunner` over `java.lang.ProcessBuilder`,
   explicitly *not* a PTY session (`GuestCommandRunner.kt` KDoc: "package
   operations must never touch (or type into) a user-visible terminal
   session"). M7.2's notification targets live in domain 1; domain 2
   already reports completion synchronously through `ExecResult`.

### 1.1 Lifecycle trace of a PTY session

```text
User opens Terminal / taps a launcher tile
        ↓
TerminalViewModel (openTerminal / newSession / openLinuxShell /
  openLinuxShellAt / openCommandApp / openCustomTool / openCatalogApp)
        ↓
TerminalSessionManager.createSession()          ← host Android shell path
TerminalSessionManager.spawnLinuxSession()      ← Alpine guest path
  (always preceded by prepareLinuxSession() on Dispatchers.IO)
        ↓
TerminalSessionManager.spawn()  — the single session factory
        ↓
new TerminalSession(...)            (com.termux.terminal.TerminalSession)
        ↓  (fork of the PTY actually happens lazily — see §1.3)
JNI.createSubprocess()              (termux.c: /dev/ptmx, fork, execvp)
        ↓
PTY master fd + child process (host: /system/bin/sh; guest: proot)
        ↓
3 threads: TermSessionInputReader (PTY→queue), TermSessionOutputWriter
  (queue→PTY), TermSessionWaiter (JNI.waitFor → MSG_PROCESS_EXITED)
        ↓
MainThreadHandler: emulator.append() → notifyScreenUpdate()
        ↓
PocketShellSessionClient callbacks → TerminalSessionManager state
```

### 1.3 Two facts that shape everything downstream

1. **The PTY child is forked lazily.** `TerminalSession`'s constructor does
   not fork; `initializeEmulator()` does, and it runs when the view first
   sizes the session (`updateSize`). The M3.5 lesson is recorded in
   `CommandApps.kt` (the PTY write path drops bytes while `mShellPid == 0`),
   which is why launch commands travel through **argv**, never PTY writes:
   `sh -l -c "<command>; exec /bin/sh -l"`.
2. **For guest sessions the direct child is `proot`, not the guest shell.**
   `spawnLinuxSession` execs `spec.executable` = `libproot.so` path
   (`RuntimeProcessLauncher.LaunchSpec.executable`). Therefore
   `mShellPid`/`waitpid`/`isRunning()`/`getExitStatus()` all describe
   **proot**. Inside it: `/bin/sh -l -c "<chain>"` → the command → on exit
   `exec /bin/sh -l` (same PID as the `-c` shell). "Session exit" and
   "command exit" are **different events** (see Part B, state 5/6).

### 1.4 Persistence and death

There is **no session persistence or restoration anywhere in the app**
(verified: no restore/SavedState path in `terminal/`). Sessions live and
die with the process. `TerminalService` is `START_NOT_STICKY` — after
Android kills the process, nothing restarts and every session is gone.
This is stated to the user in-app (editor back guard) and is the honest
baseline M7.2 must design around.

## 2. PART B — What PocketShell can actually know

For each requested state: the real signal, or an explicit "cannot know".

| # | State | Verdict | What real signal proves it (or why nothing can) |
|---|---|---|---|
| 1 | `SESSION_EXISTS` | **RELIABLE NOW** | `TerminalSessionManager.sessions` StateFlow — the manager is the process-scoped owner; every spawn/close appends/removes an entry. Authoritative by construction. (`creating` covers the spawn-in-flight window.) |
| 2 | `SHELL_RUNNING` | **RELIABLE NOW — with a naming correction** | `TerminalSession.isRunning()` (`mShellPid != -1`), flipped by the `TermSessionWaiter`'s real `waitpid`. Zero polling. **But it means "the DIRECT CHILD is alive"** — for guest sessions that is proot, not the guest shell, and it says nothing about descendants. The honest name for this state is *session running*. |
| 3 | `COMMAND_RUNNING` | **NOT KNOWABLE TODAY** | No child-process tracking exists anywhere: `waitpid` watches exactly one pid (the direct child), and the guest command is a *descendant* of proot (`proot → /bin/sh -c → <command>`). Nothing in the current architecture observes descendants. What *is* possible (Tier 2, real signal, no heuristics): enumerating the session's descendant pids via `/proc` — the app's own UID is visible under `hidepid=2` (the `getCwd()` procfs read is the in-tree precedent, and `ps`/`top` work inside the guest for the same reason). Requires an architecture change (a process-tree watcher); not available now. |
| 4 | `SHELL_IDLE / WAITING_FOR_COMMAND` | **NOT KNOWABLE — and must not be faked** | No signal exists. Output silence is explicitly rejected (spec + this audit): a compiling agent and a prompt-waiting shell are both "no output recently". The only *protocol-grade* route is shell integration (OSC 133 marks delivered from inside the shell) — possible to inject into launch chains we construct (`guestLaunchChain`), impossible to force into sessions where the user drives the shell. Not in the current architecture. |
| 5 | `COMMAND_COMPLETED` | **SESSION-LEVEL: RELIABLE. COMMAND-LEVEL: NOT TODAY.** | Real, waitpid-proven exit code for the **direct child** (`getExitStatus()`, positive = code, negative = negated signal). For host sessions spawned with `initialCommand` (`sh -c`), the direct child's exit **is** the command chain's exit — mksh `-c` propagates the last status. For guest sessions the direct child is proot: its exit means *the whole guest session ended*, not "the agent finished" (the `; exec sh -l` chain keeps the session alive after the agent exits — which is the intended UX). Agent-level completion is exactly as unknowable as state 3 today; the same Tier-2 procfs route (watch a matched descendant pid disappear) is the real-signal path. Also a wiring gap, trivially fixable in P2: `SessionEntry.isFinished` is a Boolean — `getExitStatus()` is never surfaced into the entry. |
| 6 | `COMMAND_FAILED` | **Same verdict as 5** | Same signal; "failed" = non-zero exit / negated signal on the direct child. Session-level only. |
| 7 | `SESSION_STOPPED` | **RELIABLE NOW — two distinct real events** | (a) *Process ended*: `onSessionFinished` callback → `markFinished` — entry stays visible, honestly marked. (b) *User closed the tab*: `closeSession` — SIGKILL + entry removed. Both are StateFlow transitions; nothing is inferred. |

**Summary of the honest capability line today:** PocketShell knows
session existence, direct-child (session) liveness, direct-child exit with
a real exit code, user-initiated close, and spawn-time launch metadata.
It cannot know anything about **descendant** processes (the actual agent),
**shell idle-ness**, or **agent-level completion**. Every gap that can be
closed at all is closable only with new architecture built on real signals
(`/proc` tree watching, shell-integration protocol marks, agent
integrations) — never timers or output-shape heuristics.

### 3.3 Critical question answered

> Can PocketShell reliably know "This session was launched as Antigravity"
> without inspecting terminal output?

**Yes — for launcher-tapped sessions, but only as a display string.**
The mechanism is spawn-time: the Home tile handler passes the registry
`displayName` (e.g. `"Antigravity"`) into `launchGuestCommand` → it becomes
`SessionEntry.label`. That label is real spawn-time evidence, not a guess.
Its weaknesses, honestly stated:

1. It is a **display string, not a structured identity** — nothing carries
   `CommandApp.id = "agy"`, and a user-defined custom tool *named*
   "Antigravity" is indistinguishable from the registry launcher after
   spawn (`openCustomTool` labels with `tool.name`).
2. The only surviving classification is *label + guestness-guess*
   (`guestSessionIds` lost on ViewModel recreation, `GUEST_SESSION_LABEL`
   string comparison as fallback) — two partial sources where the spec's
   own principle demands one.
3. It says nothing about the process: if `agy` exits two seconds later, the
   session still says "Antigravity" while a login shell runs.

**Cleanest attach point for real metadata** (for P3, not implemented now):
`TerminalSessionManager.spawn()` is the single factory every launch path
converges on (:188-232). Adding a structured `SpawnOrigin`/`AgentMetadata`
parameter to `spawnLinuxSession`/`createSession` → carried on
`SessionEntry` is a ~3-call-site change that makes identity authoritative,
structured, and per-session. `TerminalSession.mSessionName` exists as an
upstream slot but `SessionEntry` is app-owned and already flows to
every consumer via the StateFlow — the entry is the right carrier.

## 4. PART D — Manual commands vs known launchers

### Case A — Known launcher (tap)

Reliable. Spawn-time argv (`sh -l -c "agy; exec /bin/sh -l"`) and label
are recorded before the first byte flows (§3). This is Tier 1: metadata
from the launcher, lifecycle from the PTY.

### Case B — Manual command (`agy` typed at a prompt)

**Not reliably detectable from the session layer today, and keystroke
parsing is a heuristic — rejected.** The input path is observable in
principle (`terminal-view/TerminalView.java:783/907/923/1070` — keystrokes
reach `mTermSession.write()`), but interpreting typed bytes requires
re-implementing a shell's line editor and parser; that is precisely the
class of guessing this milestone forbids.

What **is** technically possible from the existing process architecture —
and is a *real* signal, not a heuristic:

- The interactive guest binds a **real host `/proc`** (absolute policy
  since m3.6, `RuntimeProcessLauncher.kt` KDoc; `ps`/`top` work in-guest
  for the same reason). Every session descendant runs as the app's own
  UID, so a watcher inside PocketShell can enumerate
  `/proc/<session-pid>`'s descendant tree and read `/proc/<pid>/exe`
  (canonical path — stronger than `cmdline` against wrapper renames) and
  `/proc/<pid>/cmdline`.
- Matching a descendant's executable against the registry's known command
  names (`hermes`, `opencode`, `claude`, `zcode`, `kilo`, `cline`, `agy`,
  `codex`, `qwen`) turns "is Antigravity running in session 3" into a
  procfs-evidenced answer — **including** for manually typed commands.

Classification: **Tier 2 — possible with architecture changes** (a
process-tree scanner component). Honest caveats recorded now: npm-style
CLIs `exec` through node (exe may read `…/node`, with the script path in
cmdline — matching needs both fields); binary names are registry claims
until a device pass verifies each one's actual `/proc` shape; and there is
a race window between fork and execvp where a new pid has no meaningful
exe yet.

### Case C — Nested agent/process (`bash` then `agy`; `npm script → agent`)

The procfs tree **does** see arbitrarily nested descendants (it is the
real process table, not a shell-level view) — so observation is possible
where the M7.1 session layer sees nothing. The honest limitation is
**attribution**, not visibility: when wrappers rename (`npm run` → `sh`
→ `node …/thecli`), which descendant "is the agent" requires matching on
exe/cmdline content with the ambiguity that entails. The audit's
recommendation is to treat attribution confidence as data (`matchedBy:
LAUNCH_METADATA | PROCFS_EXE | PROCFS_CMDLINE`) rather than pretending
every match is equally strong.

All nine registry agents ride the **identical** machinery (same
`launchGuestCommand` core, same proot PTY, same procfs visibility), so the
capability columns are mechanically identical; per-agent differences are
limited to how their binary shows up in `/proc`, which this audit cannot
verify from the sandbox and is marked for the P3 device pass.

|---|---|---|---|---|---|
| Hermes Agent | YES — label at spawn | YES — waitpid on proot | NO | NO | procfs descendant match on `hermes` |
| OpenCode | YES | YES | NO | NO | procfs match on `opencode` |
| Claude Code | YES | YES | NO | NO | procfs match (`claude`; likely node-hosted — verify exe/cmdline on device) |
| ZCode | YES | YES | NO | NO | procfs match on `zcode` |
| Kilo Code | YES | YES | NO | NO | procfs match (`kilo`; Bun-compiled per M3.6 history — verify) |
| Cline | YES | YES | NO | NO | procfs match (node-hosted likely — verify) |

| Codex | YES | YES | NO | NO | procfs match (`codex`; verify host runtime) |

Tier classification:

- **Tier 1 — reliable now:** session existence; session (direct-child)
  running; session exit with real exit code; user close; spawn-time
  launcher identity (label); the launched-vs-manual distinction **at
  spawn**. This is enough to power *"a session launched as Antigravity is
  running / has ended"* notifications honestly.
- **Tier 2 — possible with architecture changes (real signals, no
  heuristics):** agent-level running/completion via a `/proc` descendant
  scanner (works for manual and nested cases too); shell-integration
  (OSC 133) marks injected into launch chains we construct; bell/title as
  weak-but-real event signals.
- **Tier 3 — not reliably detectable (rejected as heuristics):**
  waiting-for-input in general (Part F); manual-command detection by
  keystroke parsing; "idle therefore waiting" of any kind.

## 6. PART F — Waiting for user input (feasibility only; nothing implemented)

**Honest verdict: PocketShell cannot reliably distinguish "agent actively
working" from "agent waiting for user input" today, and no combination of
existing signals proves it.** Signals examined:

1. **PTY reads/writes** (`MSG_NEW_INPUT`, `onTextChanged`, the write
   queues): throughput events. An agent mid-edit, a spinner, and a prompt
   waiting for input are all "output happened / didn't happen". Inactivity
   proves nothing — rejected per the spec's critical rule.
2. **Process state** (`/proc/<pid>/stat` state char): a *real* signal, but
   an event-loop-driven TUI and a blocked-read prompt both sit in `S`
   (interruptible sleep) the overwhelming majority of the time. Cannot
   separate working from waiting. Rejected as a discriminator.
3. **`onBell`** (`TerminalSessionClient.onBell` — currently `Log.d` and
   nothing else, `PocketShellSessionClient.kt:44-47`): a real,
   protocol-delivered event (BEL). Some agents emit BEL to request
   attention. It is the closest thing to a real "needs attention" signal
   that exists today — but it is (a) emitted by only some agents, (b) not
   defined to mean "waiting for input" universally, and (c) currently
   discarded. Usable in a later phase as an *attention hint*, clearly
   labeled, never as proof.
4. **Title changes** (`onTitleChanged` / OSC 0/2): real events; some agent
   CLIs set titles. Semantically unbounded (a title can say anything);
   usable only as display hints, never state.
5. **Known agent integrations**: several agent CLIs expose real
   machine-readable hooks (shell-integration escape sequences, agent
   hooks/notification endpoints). This is the only path that yields
   *proof*, and it is per-agent integration work, explicitly out of P0
   scope, and honest to schedule as its own future phase — not something
   P3 can retrofit generically.

**What this means for the phase plan:** P7 ("waiting-for-user detection")
must either (a) ship only what real signals support — bell/title-driven
*hints* with honest copy — or (b) be descoped until agent-specific
integration exists. It must not ship timeout-based guessing. This audit
recommends keeping P7 last and explicitly conditional (Part L).

## 7. PART G — Background & Android lifecycle

Verified mechanics:

- **Foreground service exists:** `terminal/TerminalService.kt` —
  `foregroundServiceType="specialUse"` (manifest :77-84 with the
  `PROPERTY_SPECIAL_USE_FGS_SUBTYPE` explanation string), started/stopped
  by `syncWithSessionState()` on **every** spawn, close, and finish
  (`TerminalSessionManager.syncService`). Runs iff ≥1 session entry
  exists; `START_NOT_STICKY`.
- **Home / background:** the process keeps running — the FGS holds it out
  of the cached/LMK-favored states. PTY reader/writer/waiter threads are
  plain Java threads; they continue. The guest processes (children of the
  app process) continue.
- **Screen lock:** nothing in the app takes a WakeLock (verified: no
  WakeLock/AlarmManager/WorkManager/JobScheduler anywhere). Processes
  continue under Doze with the usual OS-level throttling (network and CPU
  deferrals) — an external constraint, stated, not worked around.
- **Activity destroyed / process killed:** sessions are children of the
  app process (plus proot `--kill-on-exit` and PTY teardown), so **Android
  destroying the app process destroys every session**. `START_NOT_STICKY`
  means no restart; there is no session restore; the next launch starts
  empty. Under memory pressure the system *can* kill even a
  foreground-service app — the FGS lowers this risk, it does not remove it.
- **User returns (process alive):** `MainActivity` is `singleTask` with a
  broad `configChanges` set (no recreation on rotation/fold/keyboard);
  Compose ViewModels re-attach; `TerminalSessionManager` (process-scoped
  object) still owns live sessions; the terminal re-renders from the live
  emulator. The M7.1.1 `ON_RESUME` rescan pattern (MainActivity
  `LifecycleEventObserver`) is the established hook style for
  return-to-foreground re-evaluation.
- **Existing Android notifications:** exactly one — the FGS notification
  (Part H).

> **Critical question answered:** if an agent is running and the user
> backgrounds PocketShell, the process **does** continue, and the existing
> component that keeps it alive is `TerminalService` (the specialUse FGS
> started whenever any session exists). The residual risks are system
> kill under memory pressure and the user swiping the app away /
> force-stopping it — after which everything is gone with no restoration.

## 8. PART H — Existing notification infrastructure (complete inventory)

Searched the entire repository for `Notification*`, `NotificationManager`,
`NotificationChannel`, `NotificationCompat`, `PendingIntent`,
broadcast receivers, `POST_NOTIFICATIONS`. Findings:

1. **What exists — exactly one surface:** `TerminalService`'s ongoing FGS
   notification. Channel `"terminal_sessions"` (`IMPORTANCE_LOW`,
   created in `onCreate`), notification id `1`,
   `Notification.Builder` (framework, not compat — no androidx
   `NotificationCompat` anywhere), plurals text "N session(s) running",
   `setOngoing(true)`, `PendingIntent.getActivity` → `MainActivity` with
   **no extras** (tap opens the app; there is no session routing).
   Recreated on every `onStartCommand`.
2. **Permission:** `POST_NOTIFICATIONS` is declared in the manifest
   (:26) with an honest comment ("notification is hidden if the user has
   not granted this") — and **is never requested at runtime** (verified:
   no permission-request launcher anywhere; the only
   `rememberLauncherForActivityResult` uses are file/icon pickers). On
   Android 13+ the FGS notification — and any future activity
   notification — is invisible until the user grants it in Settings.
   The service still runs regardless. **This is the single largest
   ready-made gap M7.2 P1 must close.**
3. **Receivers / PendingIntents:** no `BroadcastReceiver`, no
   `registerReceiver`, no exported receivers in the manifest; the single
   PendingIntent is the FGS content intent above.
4. **What M7.2 must not duplicate:** the FGS itself and its
   session-retention notification (channel semantics: "shows when
   terminal sessions are running in the background"). M7.2 should add a
   **new channel** for activity notifications, leave the FGS
   mechanism/channel as the retention surface, and route taps through a
   new intent-extra scheme (`MainActivity` currently ignores intent
   extras entirely — and being `singleTask`, a notification tap while the
   app is alive arrives as `onNewIntent`, which nothing handles today).
5. **Reuse summary:** channel-creation pattern (TerminalService), the
   manifest permission, and the FGS lifecycle sync are the reusable
   foundation; everything else (channels, posting, routing, permission
   request, per-notification identity) is new build.

## 9. PART I — Proposed authoritative state model (design only)

**Principle:** real runtime signal → authoritative state → UI / Home /
notification. One source of truth: the **existing**
`TerminalSessionManager` — extended, never duplicated or shadowed
(the M7.1.1 lesson: one authoritative model, no local copies).

```text
REAL SIGNALS (all event-driven, zero polling)
  spawn params (launch path + argv + probe)     ← spawn time, structured
  TermSessionWaiter waitpid → MSG_PROCESS_EXITED ← real child exit + code
  closeSession (user)                            ← real removal
  [Tier 2, later] /proc descendant scan          ← real procfs evidence
  [Tier 2, later] shell-integration marks        ← real protocol events
        │
        ▼
TerminalSessionManager (the ONE owner — extended)
  SessionEntry {
    id, session, label, title, isFinished,        ← today
    exitStatus: Int?,                             ← surfaced (exists today, not carried)
    origin: SpawnOrigin,                          ← SHELL | LINUX_SHELL | COMMAND_APP(id)
    │                                               | CATALOG_APP(id) | CUSTOM_TOOL(id)
    │                                               | FILES_TERMINAL
    agent: AgentHint?,                            ← { displayName, command, matchedBy }
  }
  published exactly as today: StateFlow<List<SessionEntry>>
        │
        ▼
DERIVED PROJECTIONS (pure functions of the one state — no second truth)
  AgentActivityRepository  → "agent-relevant sessions" flows for Home + notifications
  NotificationPolicy       → user preference (DataStore, opt-in gates)
                             + real state → effective notification behavior
        │
        ▼
CONSUMERS: TerminalScreen (as today) · Home session cards (as today) ·
           NotificationCoordinator (new)
```

**Provable state machine per session** (nothing without a signal):

```text
SPAWNING (creating=true)
   → EXISTS/RUNNING        (entry present; direct child alive)
   → FINISHED(exitStatus)  (waitpid proved the child exited)
   → REMOVED               (user closed the tab)
```

Deliberately **absent** until real signals exist: `COMMAND_RUNNING`,
`AGENT_RUNNING`, `AGENT_FINISHED` (Tier 2 upgrades, scoped to P3),
`IDLE/WAITING` (no signal — Part F), any per-agent work/waiting state.

This mirrors the M7.1.1 architecture lesson exactly
(`ExternalKeyboardVisibilityModel`: persistent user preference + real
hardware state + explicit user request → effective state, single writer):
here — notification preference + real session/agent state → effective
notification behavior.

## 10. PART J — Proposed M7.2 architecture (design only)

### 10.1 Components

| Component | Responsibility | Input signals | Output state | Persistence | Lifecycle owner |
|---|---|---|---|---|---|
| `SpawnOrigin` / `AgentHint` (data, in `terminal/`) | structured launch identity on `SessionEntry` | launch-path params at the 5 spawn sites (+ Files path) | fields on the one `SessionEntry` | process-scoped (with sessions — by design) | `TerminalSessionManager` |
| `SessionActivityTracker` (logic **inside** `TerminalSessionManager`) | derive per-session activity purely from callbacks: markFinished gains `exitStatus`; no timers | `MSG_PROCESS_EXITED` (via client), `closeSession`, spawn | updated `SessionEntry` list on the existing StateFlow | none (already none) | `TerminalSessionManager` (main handler, as today) |
| `AgentActivityRepository` (new, small, process-scoped) | the ONE read model for "what is running / what finished", filtering by `origin`/`agent`; powers Home + notifications from the single source | manager StateFlow | derived flows (`runningAgentSessions`, `finishedEvents`) | none | Application-scoped object (like the manager) |
| `NotificationCoordinator` (new) | owns non-FGS channels; edge-triggered posts from **state transitions** (never polling); tap routing via intent extras; cancels stale ids on app start | repository flows + `NotificationPolicy` | system notifications | notification prefs via DataStore (`NotificationPreferences`) | Application-scoped; registered from `PocketShellApp` |
| `NotificationPreferences` (new, DataStore per-domain pattern) | user opt-in gates per notification class | Settings UI (P9) | flows consumed by the policy | **persisted** | `settings/` domain pattern |

| `TerminalService` | UNCHANGED retention FGS | unchanged | unchanged | — | unchanged |

                                     ▼

### 10.3 Provable state transitions (P2 scope)

```text
SPAWNING → RUNNING          spawn() appends the entry
RUNNING  → FINISHED(code)   waitpid callback (code = exit or negated signal)
FINISHED → REMOVED          closeSession
RUNNING  → REMOVED          closeSession (SIGKILL path)
```

Agent-level transitions (`AGENT_RUNNING → AGENT_FINISHED`) enter only via
the P3 mechanisms (launcher metadata + scanner), never by inference.

## 11. PART K — Risks and hard problems

| Risk | Why it exists | Current architecture support | Recommended future solution |
|---|---|---|---|
| Multiple simultaneous sessions | by design (the manager is a list) | full — StateFlow carries every entry | per-notification identity keyed by session id; group summary channel |
| Multiple agents, sequentially, in ONE session | the `; exec sh -l` chain keeps the session alive after the agent exits — agent end ≠ session end | none (no child tracking) | P3 scanner watches the matched descendant pid disappear = real agent-finish event; beware prompt-then-next-agent races; require re-match before re-notify |
| Agent launched manually | no spawn metadata exists for typed commands | none | P3 procfs matching (Case B); label stays "Alpine Linux" — attribution is scanner-graded evidence, never a guess |
| Nested processes (`bash; agy`, npm shims) | wrappers rename executables | `/proc` sees the whole tree; attribution is ambiguous | match exe **and** cmdline; carry `matchedBy` confidence; device-verify each agent's real shape |
| Command exit vs shell exit semantics | proot is the direct child; the guest shell chain outlives the agent | waitpid gives session-level truth only | keep session-level and agent-level states strictly separate in the model (Part I) |
| Background execution / Doze | no WakeLocks (none exist); OS throttles network/CPU | FGS keeps the process alive; nothing more is promised | document honestly in notification copy; never promise "always completes in background" |
| Android process death | sessions are children; `START_NOT_STICKY`; no restore | none by design | on next app start, cancel previously posted notification ids (stale-notification cleanup); sessions honestly gone |
| Stale notifications | non-FGS notifications can outlive the state that posted them (esp. after process death) | none yet | deterministic notification ids (session id + kind); post-time state check; startup sweep |
| App restart | empty manager; nothing to reconcile except cleanup | StateFlow starts empty | startup sweep (above) + no restoration claims in UI |
| Agent waiting for input | **no real signal exists** (Part F) | bell only, currently discarded | P7 ships bell/title-driven *hints* with honest copy, or is descoped; agent-specific integration is the only proof path |
| Notification tap routing | `MainActivity` ignores intent extras; `singleTask` delivers taps via `onNewIntent` (unhandled today) | none | intent-extra scheme (session id) + `onNewIntent`/`onCreate` handling → `TerminalViewModel.select` → navigate to terminal |
| POST_NOTIFICATIONS never requested | the manifest declares it; nothing requests it | service runs; notification invisible on 13+ until granted | P1 foundation: the runtime request (with an honest Settings deep-link fallback) |
| proot exit-code propagation | guest status passes through proot's exit | unverified on device | one device check in P3's pass (record actual codes for agent-failure exits) |
| `onBell` semantics | real event, unbounded meaning | logged and dropped today | treat as attention hint only; never map 1:1 to "waiting for input" |

## 12. PART L — M7.2 phase plan validation

The proposed plan (P1–P11) **stands with four audit-driven adjustments**;
the incremental delivery/testing strategy is preserved.

1. **P1 — Notification foundation: add the missing permission request.**
   The audit's only "nothing works without it" finding: POST_NOTIFICATIONS
   is declared but never requested (§8.2). P1 = channels + the request +
   the coordinator skeleton + startup stale-sweep. Unchanged otherwise.
2. **P2 — Session activity state engine: scope it to the provable state
   machine (§10.3) and surface the exit code.** The signal exists
   (`getExitStatus`) but `SessionEntry` drops it today. No
   command/agent-level states in P2 — they have no signal yet (Part B).
3. **P3 — Real agent detection: split into P3a (metadata propagation —
   small, pure, unblocks P4/P8) and P3b (procfs scanner — needs the
   device pass verifying each agent's `/proc` shape, including the proot
   exit-code check).** Splitting keeps the incremental strategy honest:
   P3a alone already enables reliable *"launched as X is running/ended"*
   notifications for launcher taps.
4. **P7 — Waiting-for-user detection: explicitly conditional.** Ship only
   bell/title-derived *hints* with honest copy, or descope until
   agent-specific integration exists. No timeout heuristic ever (Part F).

P4–P6, P8–P11 remain valid **in order**, with one dependency note: P6
(agent-level completion) depends on P3b; P4 (running notification) can
ship on P3a metadata + P2 session lifecycle. P10's stress matrix should
include the multi-agent-sequential-in-one-session case (the §11 race).

## 13. PART M — Test posture for P0

No production code and no speculative tests were added. This document is
the P0 artifact. Existing JVM coverage already pins the session layer's
real behavior (manager state transitions, launch chains, probe
discipline); P2's state machine will extend those suites, and P3b's
