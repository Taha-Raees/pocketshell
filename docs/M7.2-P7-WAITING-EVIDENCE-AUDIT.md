# M7.2 P7 — Trusted Waiting-for-User Evidence Audit

**Phase verdict: P7B — no production `NeedsInput` state shipped.**

The audit established that PocketShell cannot KNOW today that an agent is waiting
for the user. No channel in this architecture can carry evidence that satisfies the
phase's evidence standard, so P7 ships zero production behavior change and instead
pins the boundary as tests and documents what a future integration would require.
A high-quality negative result is the mandated outcome; a fake "needs input"
notification built on heuristics would violate the project's truth contract.

- Version stamp: **versionCode 47 / versionName 0.11.2-m7.1.1** (unchanged, P7 is internal-only).
- Production delta: **none** — exactly one new test file + two test-file ban-list edits + docs.
- The full-suite verification numbers in this document are MEASURED (§13), not predicted.

## 1. Scope and method

The mandate required audit-first: map the real agent I/O path, audit every curated
launcher, apply the evidence standard, and ship a production attention state ONLY if
the evidence deserves it. This report is that audit. Three evidence layers were used:

1. **Code-level audit** of the shipping sources at the P7 baseline (HEAD `c883486`):
   the PTY/JNI creation path, the terminal engine's parser and callback inventory,
   the session manager, the P3b detector, the P3c event engine, the
   repository/consumer/mapping/routing notification pipeline, and the launcher
   registry — every claim below carries a file-level reference.

   Tier-1/2/3 reality ranking), the P3a detection matrix (rejected signal classes),
   the P3b contract, the P4/P5/P6 phase docs and the ROADMAP's standing rejections.
3. **Consulted external documentation** (mandate Part C allowed this): vendor docs
   and public issue trackers for the curated agents' machine-readable channels.
   The raw search evidence rides with the repo at `scripts/p7-search/*.json`.

Nothing was implemented before the audit was complete, per the mandate.

## 3. What PocketShell can actually observe (Part B)

### 3.1 The byte path

The child process is forked from the JNI layer with a clean environment
(`clearenv()` then exactly the env the JVM passes — `termux.c:98-99`); stdin and
stdout/stderr are the PTY. Raw PTY output flows on a reader thread into a
**package-private** `ByteQueue` and then into `TerminalEmulator.append`
(`TerminalSession.java:133-148, 342-347`); **no component outside the vendored
emulator ever sees a raw PTY byte**. Input is the reverse door: every keystroke,
paste, and even the emulator's own protocol replies converge on the single
`TerminalSession.write` path, and the kernel line discipline echoes user input back
onto the same output stream. The stream is completely untagged — there is no
provenance, no timestamp, and no attribution of who produced which byte.

### 3.2 The structured-seam inventory (exhaustive)

The emulator's parser exposes exactly these structured events to the app:

| Seam | Trigger | Where it lands today |
|---|---|---|
| `onTitleChanged` | OSC 0/1/2 window title | tab label storage (`TerminalSessionManager.refreshTitle`) |
| `onColorsChanged` | OSC 4/10/11/12/104/110/111/112 | repaint |
| `onCopyTextToClipboard` | OSC 52 | system clipboard |
| `onBell` | BEL | `Log.d` and nothing else |
| `onTerminalCursorStateChange` | DECSET 25 | ignored |
| `onSessionFinished` | process exit (`waitpid`) | P2 lifecycle authority |
| `onTextChanged` | any screen change | repaint |

OSC 133 (shell integration), OSC 9;4 (progress), OSC 777 (notify) and APC
sequences are parsed and **silently swallowed** (`TerminalEmulator.unknownParameter`
behind `LOG_ESCAPE_SEQUENCES = false`). There is no callback for any of them.

### 3.3 The negative findings (repo-verified)

- No file watchers (`FileObserver`/`ContentObserver`), no broadcast receivers, no
  sockets, no MCP, no IPC — zero matches across app sources and the manifest.
- No per-session env var exists (the guest env is a fixed proot set;
  `environmentExtras` exists as a mechanism but no production caller uses it).
- No runtime "generation" concept exists anywhere — identity is the manager's
  monotonic `sessionId` (process-scoped) plus the fork-proven `shellPid`.
- No app logic reads rendered terminal text (copy/selection and accessibility live
  inside the vendored view only).
- The app stages **nothing** agent-specific into the guest: no settings files, no
  hooks config, no `--output-format`/`--json`/notify flags — every curated launcher
  is a bare command delivered as `/bin/sh -l -c "<cmd>; exec /bin/sh -l"`, and the
  trailing `exec` structurally discards the agent's exit status.
- Full-screen/TUI agents change nothing observable: the alternate screen buffer is
  internal to the emulator, and /proc detection is purely process-based.

### 3.4 The ten audit answers (condensed)

1. **Raw PTY observation** — no; bytes are unreachable outside the emulator module.
2. **Terminal state without scraping** — partially; title/colors/bell/cursor/exit
   and /proc are real, and rendered text is technically reachable but unused.
3. **Distinguish agent vs shell vs TUI vs user output** — no; one untagged stream,
   echoed input included; the only attribution available is *which process is alive*.
4. **Structured markers/events in the engine** — only the seam inventory in §3.2;
   nothing that means "waiting".
5. **Documented machine-readable signals from supported agents** — not wired and
   not present in-repo; per-agent external findings in §4.
6. **OSC/hooks/JSON/MCP/IPC channels available app-side** — none beyond §3.2 plus
   /proc scanning; no receiver machinery of any kind exists.
7. **Would any such channel require modifying the agent command?** — yes, for every
   candidate: hooks/notify/plugins are configured through agent config files or
   launch flags, and PocketShell launches bare commands with no config staging.
8. **Authoritative association with session / agent identity / generation** —
   sessionId + registry identity yes (spawn-time metadata + exact-token /proc
   correlation), **generation no** (no such concept exists).
9. **Stale evidence survival** — no; runtime state is in-memory, pruned on
   eligibility loss, tombstoned on session end, and nothing persists across
   process death.
10. **Full-screen/TUI agents** — no observable difference (§3.3).

## 5. The evidence standard applied (Part D)

The mandate allows a production `NeedsInput` state only if a candidate satisfies
ALL eight conditions. Applied honestly:

| Candidate | 1 live-session bound | 2 generation bound | 3 not arbitrary-text-triggerable | 4 defined invalidation | 5 not surviving termination | 6 replay/dedup safe | 7 no screenshot polling | 8 no inactivity inference |
|---|---|---|---|---|---|---|---|---|
| Claude hooks (permission arm) | no (no receiver) | no (no generation concept) | yes | designable | designable | designable | yes | yes (permission arm) |
| Claude `idle_prompt` / any idle timer | no | no | yes | no | — | — | yes | **NO — rejected** |
| Codex `notify` (turn-complete) | no | no | yes | unclear (semantics ≠ waiting) | — | — | yes | yes |
| OpenCode plugins | no | no | yes | designable | designable | designable | yes | yes |
| BEL (`onBell`) | yes | n/a | **NO — `printf '\a'` rings it** | no (unbounded semantics) | — | — | yes | yes |
| OSC 0/2 title text | yes | n/a | **NO — `printf '\033]2;…\007'` sets it** | no | — | — | yes | yes |
| OSC 9/777 notify body | no | n/a | **NO — same spoofability** | no | — | — | yes | yes |
| Terminal text regex / prompt shapes | yes | n/a | **NO — that IS arbitrary text** | no | — | — | **NO (scraping)** | — |
| Inactivity / CPU / process sleep | yes | n/a | yes | no | — | — | yes | **NO — rejected** |
| Local agent state files | no | no | yes | no (undocumented contracts) | — | — | yes | yes |

**Decision: the threshold is not met.** Every candidate fails at least one
condition, and the failures are structural (missing receiver, missing generation
concept, missing binding, or inherent spoofability), not matters of tuning. The
protocol-level seams that exist today (BEL, title) are demonstrably triggerable by
arbitrary output — a one-line `printf` defeats them — so they can never be
authoritative evidence, only display hints.

## 6. Accepted evidence sources

**None.** P7 accepts zero new evidence sources into production truth. The P0
audit's verdict stands and is now re-verified at the P7 baseline: PocketShell
cannot reliably distinguish "agent actively working" from "agent waiting for
user input", and no combination of existing signals proves it.

## 7. Rejected heuristics (Part J — documented as rejected, never shipped)

All of the following were considered and REJECTED by this audit; none exists in
production, and the new boundary tests (`AgentRuntimeWaitingEvidenceBoundaryTest`)
hold several of these rejections structurally:

- regex over terminal output / prompt text / `?` / yes-no strings / numbered
  choices — arbitrary text, self-defeating as evidence;
- rendered-screen scraping — nothing in the app layer reads the terminal buffer
  (pinned);
- terminal inactivity, CPU inactivity, elapsed timers, process sleep state —
  cannot separate "working" from "waiting" (the P0 audit's Tier-3 rejection);
- BEL or title-driven waiting claims — protocol-real but semantically unbounded
  and spoofable (display hints at most, and today not even that: BEL is logged
  and dropped);
- exit-code-derived state — structurally unavailable (the `sh -c; exec` chain
  discards the agent's exit status) and semantically wrong anyway (exit is not
  waiting; exit 0 is never success);
- OSC 9/777 message bodies — unboundable strings, and wiring them would mean
  modifying the frozen vendored emulator for evidence that still fails the
  standard.

## 8. Stale-request model (future design, documentation only)

If a future phase ever wires trusted attention evidence, the request identity
MUST be the tuple **(sessionId, runtimeGeneration, requestId/evidence id)**, and
the attention state MUST be cleared when any of these occurs: runtime
disappearance (P3b NoLongerDetected), runtime generation change, session close
(P2 SESSION_ENDED), request resolution (a corroborating structured event from the
same channel), process death, or app-level invalidation. Process death must never
fabricate restoration: a recreated process is a NEW generation with no live
requests until the authoritative source re-asserts them. Today's architecture has
no generation concept — this model is recorded here as the design target that a
future integration must build (and test) first.

## 9. Multi-session model

The existing pipeline already isolates per session: events carry `sessionId`,
notification identity is `AGENT_RUNTIME_BASE + sessionId`
(`NotificationIds.agentRuntime`), the P6 matrix pins one-identity-per-story
folds, and the P5 route carries only the authoritative session id with stale-id
degradation to OpenApp. A future attention state must ride the same keying:
session 2's "needs input" may never update session 1's notification, navigate to
session 1, write to session 1, or clear session 3's state — and the tap route for
an attention surface must resolve through the same pure
`AgentRuntimeNotificationRouting.resolve` seam. No cross-session contamination
exists today, and none may be introduced.

## 10. Notification behavior (Part F — not shipped)

No attention wording ships. The running surface continues to say exactly
"`<Name> is running`", unknown stays "`<Name> runtime unknown`", withdrawal stays
cancellation-only, and exit facts stay factual. For the future: if evidence proves
only a permission request, the wording must be the narrower claim
("`<Name> is requesting permission`"), not the broader "needs input" — the
mandate's wording rule is recorded here so a future integration cannot
overgeneralize. The wording ban lists extended by P7 (`needs input` joined the
transition-matrix produced-wording sweep and the shipped-literal sweep) will need
a conscious, documented revision before any such wording can legitimately ship.

## 11. Notification response actions (Part G — NOT shipped)

**TAP-TO-TERMINAL remains the only interaction.** The notification layer contains
no write path at all (pinned by test): no `TerminalSession` reference, no
`write`/`paste` machinery. A future "answer from the notification" action is safe
only when ALL of the following are provable at interaction time: the exact
request is still current (not superseded), the response mapping belongs to that
exact structured request (agent-defined choices, never invented), the target
session and runtime generation still match, and replay cannot answer a newer
prompt (request identity consumed exactly once). Until a structured request
channel with those properties exists, injecting keystrokes such as "Yes" →
`1\n` into the PTY is forbidden — the boundary test holds this structurally.

## 12. Truth guarantees (explicit)

P7 confirms, for the whole shipping surface:

- **no inactivity inference** — no timer, CPU, or sleep-based state anywhere;
- **no text-regex waiting inference** — no terminal text is read at all (pinned);
- **no completion inference** — the event vocabulary remains exactly
  Launched / ConfirmedRunning / NoLongerDetected / RuntimeUnknown / SessionEnded
  (pinned since P3c);
- **no success/failure inference** — exit facts stay verbatim; exit 0 is never
  success (pinned since P4);
- **no arbitrary PTY response injection** — the notification layer has no write
  path (pinned by P7);
- **no completion/success/failure/waiting claim in any produced or shipped
  string** — the ban lists now cover `waiting for input`, `needs attention` AND
  `needs input`.

## 14. What a future trusted-attention integration would require

In dependency order, per this audit:

1. **A versioned evidence contract per agent** — starting from the class-B
   channels documented in §4 (Claude Code hooks first). The P3a matrix already
   classifies an app-owned environment-variable handshake as "potentially
   trustworthy … not implemented": the guest env is composed by
   `RuntimeProcessLauncher`, so a per-session identity variable (binding the
   agent's hook payload to the PocketShell sessionId) is the one seam the app
   already owns end-to-end.
2. **A runtime-generation concept** — required by the stale-request model (§8)
   before any attention state can be invalidated correctly.
3. **An app-side receiver** — a watcher/IPC endpoint for the agent's structured
   output, added WITHOUT touching the vendored emulator and WITHOUT scraping.
4. **A launcher-staging policy decision** — today every launcher is a bare
   command and the app stages nothing; staging hooks/notify config is a product
   decision that must be taken explicitly, not slipped in.
5. **Event-vocabulary extension** — a narrowly scoped typed attention event
   (Runtime state RUNNING + Attention state NEEDS_INPUT/REQUESTING_PERMISSION as
   orthogonal axes), never a re-labeling of RUNNING, consumed through the
   existing P3c → repository → P4 mapping → coordinator chain.
6. **The §8 stale-request model and §9 multi-session tests**, plus device-gate
   steps proving a REAL agent request end-to-end (TESTING §56's future Part B
   shape).
