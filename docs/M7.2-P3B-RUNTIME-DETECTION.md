# M7.2 P3b — Runtime Agent Detection via `/proc`

**Phase:** runtime evidence layer (audit + experiments + implementation).
**Baseline:** the M7.2 P3a record tip (launch-identity model + truth
boundaries shipped, 833/833 JVM green). **No user-visible change, no
notifications, no completion claims, no version bump.**

P3a established the identity/truth boundary — **Launched ≠ Running ≠
Completed** — and could honestly prove only the first statement. P3b
investigates and implements the next level:

> PocketShell has **runtime process evidence** that agent X is currently
> running — or it honestly has none.

The answer below comes from the real sources, the real process
architecture, and controlled procfs experiments — not assumptions.

---

## 1. The real process architecture (discovered, not assumed)

Every guest session converges on `TerminalSessionManager.spawnLinuxSession`
→ the termux JNI PTY (`fork` + `setsid` + `execvp`):

```text
PocketShell app process (UID U, SELinux untrusted_app)
└── proot                                    ← PTY's DIRECT child (JNI waitpid sees ONLY this)
    │   setsid() in the JNI child → proot IS the session+group leader (pgid == its pid)
    │   argv: [...proot flags..., /bin/sh, -l, -c, "<command>; exec sh -l"]
    └── /bin/sh -l -c "<command>; exec sh -l"
        └── <command>                          ← e.g. kilo — a DESCENDANT, invisible to waitpid
            └── (agent helper/worker children)
```

Load-bearing facts, each pinned by source or experiment:

- **The direct child is proot** (P0 audit §1.3) — session lifecycle truth
  (P2: STARTING→RUNNING→FINISHED + structured exit status) is proot's
  story, never the agent's.
- **The chain shell carries the whole command line as ONE argv element**
  (experiment E2): `sh -l -c` holds `"kilo; exec sh -l"` as a single
  element — exact-element matching can never hit the shell.
- **After the agent exits, the exec'd login shell keeps the session
  alive** — session RUNNING at the prompt is not agent RUNNING (P3a's
  truth-loss point 2, unchanged).
- **Guest processes all run as the app's own UID** (proot translates
  paths; it does not change identity) — and the interactive session binds
  real host procfs with `hidepid=2` (docs/PROCFS-CONTRACT.md §1). The
  same-UID view is exactly what the app can read, host-side or guest-side.
- **In-tree precedent**: `TerminalSession.getCwd()` already reads
  `/proc/<pid>/cwd` from the app — same-UID procfs access is an established,
  working mechanism in this codebase (P0 audit line 78).

## 2. `/proc` capabilities (controlled experiments, scripts/procfs_experiments_p3b.sh)

Ran on real Linux procfs (the sandbox is x86_64, the device aarch64 —
procfs semantics are ABI-independent). The sandbox has NO real registry
agent binary; experiment shapes used stand-ins (a resident-interpreter
shebang script named `claude`, a copied ELF named `kilo`) and are labeled
as such — mechanism validation, never fake agent evidence.

| # | Question | Result |
|---|---|---|
| E1 | Can a same-UID reader see a known process? | `/proc/<pid>/cmdline`, `stat` (state/ppid/pgrp), `exe` (readlink), `status` all readable; the ppid chain reaches the launcher. |
| E2 | What does the launch chain look like? | Tree = chain-shell → command child, both sharing the launcher's process group; the chain rides ONE argv element of the shell; the command's `argv[0]` IS the token; **no chain-shell argv element equals the token** (exact-element matching cannot false-hit the shell). |
| E3a | Interpreter-hosted CLI shape (npm-style) | Kernel shebang contract: argv = `[interpreter, scriptPath, ...]` — the invoked name rides **argv[1]** with its basename == token; `exe` reads the INTERPRETER (so an exe-only matcher would miss this shape). |
| E3b | Single-file binary shape (bun-style) | `exe` basename == token directly (strongest evidence); argv[0] is the path with the same basename. |
| E4a | Do orphans escape attribution? | The orphaned grandchild **reparents to init (ppid chain LOST) but KEEPS its process group** — pgid membership still attributes it. The two domains complement each other. |
| E4b | The blind spot | A `setsid`-ed helper that later orphans (double escape) is in NO domain — honestly invisible, no claim in either direction. |
| E4c | Negative control | Unrelated same-name processes outside the session tree share neither the chain nor the group — structurally unattributable to the session. |
| E5 | Reader visibility scope | Non-root reader: own-UID cmdline/stat/exe fully readable. Android's `hidepid=2` additionally makes foreign-UID processes INVISIBLE in the listing; the exact device-side SELinux behavior of `exe` readlink is recorded as the device gate (§7). |

**What Android adds** (documented, device-gated): hidepid=2 restricts the
readdir listing to app-UID processes (tens, not hundreds — this is also
what makes the scan cheap); SELinux governs `exe` readlink for the app's
own context — the getCwd() precedent plus `ps`/`top` working in-guest
make same-UID readability the expected case, verified on device in
TESTING §51.

## 3. The correlation mechanism (PART F — the anti-false-positive core)

A process is attributed to a session ONLY through that session's
**fork-proven correlation root** — the direct-child PID recorded by the
manager on the REAL fork signal (`SessionEntry.shellPid`, new in P3b: set
in `markStarted` from `session.getPid()` on the main thread, exactly when
STARTING→RUNNING is accepted; `0` while STARTING). Two attribution
domains, both derived from the root and both SAFE by kernel semantics:

1. **PPID-chain descent** — walking parent links reaches the root.
   Covers descendants that left the original process group (job control,
   worker pools). Kernel-safe: you can only be in this chain by descent.
2. **Process-group membership** (`pgrp == rootPid`) — the root called
   `setsid()` (termux JNI child), so it IS the group leader; membership
   requires descent from it or an explicit move within its session.
   Covers orphans (E4a: ppid lost, group kept).

The scanner uses the **union**. A process anywhere else on the device —
even running the identical binary — belongs to a different chain and a
different group and can NEVER satisfy either domain against a session
root it does not descend from. "A random process elsewhere must never
produce RUNNING" holds structurally, not by policy.

## 4. Matching rules (PART G — no substring matching, ever)

`AgentProcessMatcher.match(token, process)` — pure, in confidence order:

1. **PROCFS_EXE** — `basename(readlink(/proc/<pid>/exe)) == token`.
   The actual executable image (single-file binaries: bun-compiled kilo,
   static musl agy). For interpreter-hosted CLIs the exe reads the
   interpreter, so this grade does not fire there (E3a).
2. **PROCFS_CMDLINE** — the token appears as an EXACT argv element:
   - `argv[0] == token`, or basename(argv[0]) == token when argv[0] is a
     path; or
   - `argv[1]` is a path whose basename == token — the kernel shebang
     contract's script position (E3a).

Safety properties (each pinned by tests): substring containment never
matches (`codex` ≠ `my-codex-wrapper`/`codex-helper`/`something-codex`);
the chain shell's single-element command line cannot match (E2); a bare
word at argv[1] (e.g. `npm exec kilo`) is treated as an argument, not a
script; a blank token never matches; unreadable fields claim nothing.

Confidence is DATA: the grade travels with the claim
(`AgentMatchedBy.LAUNCH_METADATA | PROCFS_EXE | PROCFS_CMDLINE` — the
ROADMAP-named compile-time-forced extension), so a consumer always knows
HOW a claim was established.

**Residual limitation (recorded, accepted):** a long-lived CORRELATED
process whose argv[1] is exactly a path named `<token>` (e.g. an editor
opened on a directory named after the agent) would match rule 2.
Correlation already confines candidates to the agent session's own tree;
the grade records which rule fired so a later phase can tighten. Per-agent
true `/proc` shapes (codex/zcode/hermes/cline/qwen host runtimes) remain
the §51 device pass — shapes matching neither rule yield UNKNOWN, never a
false RUNNING.

## 5. The runtime state model (PART E — nothing invented)

```text
enum AgentRuntimeState { NOT_APPLICABLE, UNKNOWN, NOT_RUNNING, RUNNING }
```

| State | Meaning | Evidence |
|---|---|---|
| NOT_APPLICABLE | Plain shell, known non-agent tool (nano/htop/vim/git/python3), custom/unknown launcher. No agent claim applies — the scanner never runs for these. | the P3a classifier (structural) |
| UNKNOWN | An agent identity is expected but runtime evidence cannot currently prove a state: never observed (not-started-yet vs already-exited are indistinguishable to a scanner that never saw it), scan failed, or ambiguous evidence. **Never shown as RUNNING.** | absence of process evidence |
| NOT_RUNNING | The scanner previously OBSERVED a matching correlated process and now finds none (gone, or zombie). **Not completion** — disappearance is not success, not failure, not "finished". | proven absence after proven presence |
| RUNNING | At least one correlated process matched the token by PROCFS_EXE or PROCFS_CMDLINE right now. The observation carries the exact pids + grade — the scanner can always answer "what process caused this claim?". | live process evidence |

Decision table (all pinned in `AgentRuntimeDetectionTest`): first scan no
match → UNKNOWN; match → RUNNING(+evidence); proven presence then gone →
NOT_RUNNING; scan failure → UNKNOWN (history preserved — missing evidence
is not absence); previously-matched pid alive but unreadable → UNKNOWN
(ambiguous); previously-matched pid zombie → NOT_RUNNING; session not yet
forked (rootPid 0) → UNKNOWN; relaunch inside the session → RUNNING
again. `compute` is PURE: identical inputs always yield identical outputs.

## 6. Polling design (PART H — conservative by construction)

- **Interval**: `SCAN_INTERVAL_MS = 2000` — one /proc pass per tick.
- **Activation**: the monitor observes the manager's authoritative
  `sessions` StateFlow and extracts LIVE sessions classified exactly
  `LaunchIdentity.KnownAgent` (the P3a resolver, not a name heuristic).
- **Parking**: `collectLatest` cancels the tick loop whenever eligibility
  changes; an EMPTY eligibility set parks the monitor with zero scheduled
  work — no timers armed, no scanning, nothing after the last agent
  session is gone or finished.
- **Cost**: one readdir of the hidepid-truncated /proc (app-UID processes
  only — tens) + ≤3 small file reads per process, every 2s, only while an
  agent session exists. Microseconds of CPU per tick; no AlarmManager, no
  WakeLock, no WorkManager, no device wakes — the terminal FGS already
  keeps the process alive while sessions exist, and the scan dies with it.
- **Logging as the diagnostic channel** (PART M: existing logs, no
  debugging UI): every state transition logs `session N: X -> Y (pids=…,
  grade=…)` at Log.d under `AgentRuntimeDetector`.

## 7. Known limitations (honest, each by design)

1. **Double escape**: a process that BOTH reparents (orphan) AND leaves
   the process group (setsid) is invisible to both domains — no claim in
   either direction (E4b).
2. **Exec-style wrappers that replace themselves** (`#!/bin/sh` + `exec
   <something-else>`) lose the invoked name entirely — shapes like that
   yield UNKNOWN, never a guess.
3. **argv[1]-path residual risk** (§4): accepted, graded, documented.
4. **Per-agent shapes unverified**: which registry agents actually match
   PROCFS_EXE vs PROCFS_CMDLINE (node-hosted? bun-compiled? static?) is
   the TESTING §51 device pass — the matcher handles both proven shapes
   and degrades honestly on anything else.
5. **Android procfs specifics** (hidepid listing behavior, SELinux exe
   readlink for the app's own context): device-gated (§51); the in-tree
   getCwd() precedent and in-guest ps/top make same-UID readability the
   expected case.
6. **PIDs are not authenticated**: a correlated match is evidence, not
   proof of WHICH binary inside a wrapper chain is running. The grade
   records the shape; the claim stays "a process matching the launch
   token of this session's agent is running", which is exactly what P3b
   can honestly say.
7. **Fork/exec race**: a pid observed between fork and execvp has no
   meaningful exe/argv yet — it matches nothing (no false RUNNING); the
   next tick settles it.

## 8. Truth guarantees

### What P3b CAN prove

- PocketShell launched a specific known agent in a specific session
  (P3a, spawn metadata — unchanged).
- **A process matching that agent's launch token, inside that session's
  fork-proven process tree, is running right now** — with the pids and
  the match grade that caused the claim.
- **That previously-observed process is no longer running** (proven
  absence after proven presence) — NOT_RUNNING, explicitly not completion.
- When runtime evidence cannot support a claim: UNKNOWN — and the model
  makes UNKNOWN representable so absence of evidence is never dressed up.

### What P3b CANNOT prove (and does not model)

- That the agent COMPLETED, SUCCEEDED, or FINISHED — the agent's exit
  status is structurally discarded by the launch chain (P3a truth-loss
  point 3); the runtime vocabulary contains no completion state.
- That the agent is waiting for user input, idle, or "working" — the P0
  audit's Tier 3 rejections stand; no process state can separate them.
- Anything about custom tools or non-agent catalog tools — the scanner
  never activates for them (PART K/L), and the repository projection maps
  them to NOT_APPLICABLE explicitly.
- Anything about processes outside a session's fork-proven tree.

## 9. Implementation boundary (what was actually added)

- `terminal/AgentRuntimeDetection.kt` (new, PURE — no Android, no I/O,
  no manager reference): `AgentRuntimeState`, `ProcfsProcess`/
  `ProcfsSnapshot`/`ProcfsReader`, `AgentProcessMatcher`,
  `AgentDescendantCorrelator`, `AgentRuntimeDetection.compute/prune`.
- `terminal/RuntimeAgentDetector.kt` (new, the runtime seam): the
  observing monitor (collectLatest parking loop), `HostProcfsReader`
  (comm-aware stat parsing, NUL-split cmdline, exe readlink), the
  observations StateFlow, the Log.d evidence log.
- `TerminalSessionManager`: `SessionEntry.shellPid` recorded ON the real
  fork signal (correlation root); `spawn` wakes the detector
  (`ensureStarted`, idempotent). ONE lifecycle authority — no transition
  path touched, no second engine.
- `SessionLifecycle.kt`: `AgentMatchedBy` gains the ROADMAP-named
  PROCFS_EXE / PROCFS_CMDLINE grades (compile-time-forced extension).
- `AgentActivityRepository.runtimeActivities`: the derived four-state
  projection (manager state + detector evidence); stores nothing, decides
  nothing.
- Tests (+49 JVM per variant): `AgentRuntimeDetectionTest` (38 pure — the
  full matching/correlation/state matrix incl. the mandated negatives) +
  `AgentRuntimeDetectionIntegrationTest` (11 structural — no
  notifications, no completion claims, no output heuristics, no
  custom-tool promotion, /proc confined to the reader, the minimal
  manager extension, observer-only detector, the polling discipline) +
  the two P3a pins evolved exactly as the ROADMAP authorized (completion
  vocabulary banned everywhere with the running-state vocabulary confined
  to the evidence seam; AgentMatchedBy now exactly three grades).

## 10. What the device pass must verify (TESTING §51)

The JVM suite pins every pure and structural boundary. What only hardware
can answer: the real registry agents' `/proc` shapes (which grade fires
per agent), hidepid=2 listing behavior, SELinux treatment of `exe`
readlink for the app's own processes, and the end-to-end scan while a
real agent runs. The APK ships the mechanism; §51 exercises it honestly.
