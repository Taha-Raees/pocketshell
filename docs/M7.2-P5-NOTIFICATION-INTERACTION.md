## 1. The one-sentence contract

A tap on an agent-runtime notification opens PocketShell into the terminal
context of the session the notification already names — and does NOTHING
else: no rediscovery, no resurrection, no re-labeling of any runtime truth,
and not one byte of P4's wording changes.

P5 is the second user-visible M7.2 phase. What changed is what the user's
finger can DO; what the shade may SAY is byte-identical to P4. The honesty
line is absolute and was not renegotiated: PocketShell still knows only what
P2/P3c/P4 knew — launched / confirmed running / no longer detected / runtime
unknown / the session's own exit fact. P5 proves **navigation**, never
completion, never success, never failure, never waiting-for-input.

## 2. The interaction contract (the mandate's Part D arms)

| Notification | Tap → what the user gets | What the tap NEVER does |
|---|---|---|
| ConfirmedRunning — "<Name> is running / Agent process confirmed in terminal session N" | PocketShell opens into session N's terminal context | rediscover the process; rerun the detector; touch /proc |
| RuntimeUnknown — "<Name> runtime unknown / …" | PocketShell opens into session N's terminal context (uncertainty is not absence — the user lands where the runtime lives) | claim stopped/completed/failed; fabricate certainty |
| SessionEnded (eligible factual exit) — "Session ended / Terminal session N exited (code X)" | PocketShell opens into session N's tab **if that context still exists** (a finished-but-listed tab honestly shows its end state); if the tab is gone, PocketShell opens normally | recreate the session; respawn the process; present the historical fact as current state |
| any of the above, stale id | PocketShell opens normally (the system resume IS the action) | fake restoration; fake selection; a crash |

## 3. The routing path (Part E — the smallest existing seam)

```text
Notification (AGENT_RUNTIME kind, id = AGENT_RUNTIME_BASE + sessionId)
   ↓  PendingIntent (request code = THE notification id; FLAG_IMMUTABLE |
      FLAG_UPDATE_CURRENT) — deterministic per session, pairwise distinct
Intent(MainActivity): EXTRA_ROUTE = "open_session"
                      EXTRA_SESSION_ID = <the same authoritative sessionId>
   ↓  the ONE existing handler (cold: onCreate / warm: onNewIntent)
MainActivity.handleNotificationIntent → NotificationRoute.fromIntent
   ↓  (a missing/malformed id degrades to OpenApp here — never a crash)
pendingSessionTarget: Long?   (one Activity-scoped state; set, never queued)
   ↓  consumed EXACTLY ONCE in PocketShellRoot (LaunchedEffect)
AgentRuntimeNotificationRouting.resolve(route, liveSessionIds)   ← PURE
   ↓ live                                  ↓ stale/absent
terminalViewModel.select(id)              nothing: the resume already
screen = "terminal"                       WAS the normal open
   ↓
TerminalScreen renders the session exactly as it is
```

The seam reuses: the P1 routing extra contract (extended, not replaced), the
P1 content-intent builder (kind-aware now), the Activity's single intent
handler, the root composable's existing `screen`/`selectedId` state, and the
ViewModel's existing `select(id)`. No new navigation state, no second
handler, no second lifecycle owner.

## 4. The pure resolution model (Part J)

`AgentRuntimeNotificationRouting` is data-in/data-out with zero imports: a
tapped `NotificationRoute` plus the manager's authoritative live-id set
yields `OpenSession(id)` or `OpenApp`. Because it is pure, the entire
Part-J matrix is JVM-pinned (AgentRuntimeNotificationRoutingTest):

- confirmed-running + valid session → OpenSession(id)
- runtime-unknown + valid session → OpenSession(id) (uncertainty ≠ absence)
- session-ended + listed session → OpenSession(id) (the tab shows its truth)
- stale session (absent from the live list, or an empty list) → OpenApp
- missing/malformed session identity → OpenApp (degraded at parse, never
  seen as a fabricated target by the resolver)
- multiple sessions → each id resolves to ITSELF; a wrong-session tap is
  distinguishable; determinism is pinned (identical inputs → identical
  outcomes)
- identity (Part I): the request code IS the notification id, and the
  agent-runtime id space is pinned pairwise-distinct — session A's tap can
  never mutate session B's surface or PendingIntent

Abstraction was NOT added for its own sake: this is the one decision point
that needed JVM testability; everything Android-shaped (Intent extras,
PendingIntents, activity state) stays in the two thin adapters.

## 5. Identity (Part I)

Unchanged from P4, extended exactly once: the notification id remains
`AGENT_RUNTIME_BASE(20_000) + sessionId`; the content-intent request code
remains the notification id; the intent now also carries
`EXTRA_SESSION_ID`. Because both the id and the request code derive from the
same authoritative session id, an in-place surface update and its tap target
can never drift apart, and FLAG_UPDATE_CURRENT re-targets the SAME session's
PendingIntent rather than colliding with another session's.

## 6. The stale-safety argument (Part F)

Stale ids arise three ways; all three resolve honestly:

1. **Session closed, process alive** — the id leaves the manager's list →
   resolve → OpenApp → nothing happens beyond the resume. (The running
   surface for that session was already cancelled by P4's SessionEnded
   handling; the exit-fact tap degrades the same way once the tab is
   removed.)
2. **Process death + relaunch through a notification** — sessions are
   process-scoped and never restored; the fresh manager's list is empty →
   every session target degrades to OpenApp. A notification can never
   resurrect what the process lost: the app opens normally and stays silent
   about runtimes it cannot know anything about (P4's nothing-restored rule
   is upstream of P5 and untouched).
3. **Activity recreation (rotation/config change)** — the launch intent is
   re-delivered and re-resolves to the same outcome (idempotent); a session
   closed between recreation steps degrades exactly like case 1.

The startup stale-notification sweep (P1) is untouched: it still cancels
exactly the ledgered ids, so no notification survives a process restart to
even OFFER a stale tap — case 2 is defense in depth, not the primary
mechanism.

## 7. What P5 proves

- An agent-runtime notification can reliably navigate the user into the
  PocketShell terminal session the notification names — across cold start,
  warm resume, multi-session, and multi-agent cases.
- The interaction is deterministic (same id + same live list → same
  outcome), idempotent (Activity recreation re-resolves to the same result),
  and stale-safe (absent ids can only ever open the app normally).
- Notification interaction can be added with ZERO new permissions, ZERO new
  channels, ZERO manifest delta, and ZERO wording changes — the truth
  contract and the interaction layer are fully separable.

## 8. What P5 does NOT prove

P5 adds no evidentiary power. Explicitly still unproven and unrepresentable:

- **Agent completion / success / failure** — no such detection exists; the
  exit fact remains a statement about the terminal session's own waitpid
  status, and exit 0 is still never success.
- **Waiting-for-input / needs-attention** — nothing listens for it; no
  action offers it.
- **"The agent is still working"** — a running surface still means exactly
  "process confirmed by the P3b evidence", nothing more.
- **Any ability to control the agent** — P5 ships no Stop/Restart/Resume
  action (Part G: navigation is not control; no authoritative operation
  exists for those verbs).

## 9. Known limitations

1. **The exit-fact tap on a still-listed finished tab lands on the dead
   session's view** — honest but can look anticlimactic; the tab shows the
   session's real end state, which is the point.
2. **A tap cannot create a session** — if the user removed the tab, the tap
   opens the app normally; re-running the agent is the user's own next step,
   by hand, as it always was.
3. **PendingIntent extras are not part of Intent filter-equality** — the
   per-session distinctness rests on the request code (= the notification
   id). This is deterministic by construction and pinned by tests, but it is
   the load-bearing mechanism and is called out here honestly.
4. **SESSION_ACTIVITY notifications keep the P1 open-app tap** — P5 routed
   the agent-runtime class only; extending the P1 class was neither needed
   nor mandated (freeze discipline).
5. **Rotation re-resolves the launch intent** — by Android contract the
   activity re-reads its launch intent; a user who rotated mid-something
   after tapping gets navigated again (to the same session — idempotent, but
   observable).

## 11. The structural pins (what the tests enforce forever)

`AgentRuntimeNotificationInteractionIntegrationTest` reads the shipped
sources (comments stripped) and fails the build if the P5 surface ever:
touches `/proc` or process identity; references the detector; reaches the
session manager directly from the UI file or spawns/closes sessions from the
notification layer; builds a PendingIntent whose request code is not the
notification id, or uses hash/random identity; loses the exhaustive
kind-to-route `when`; adds permission machinery or changes the manifest's
permission set; ships a string claiming completed/success/finished/failed;
references `terminal_sessions`/`startForeground` (the FGS) from the tap
path; or adds a third notification channel. The routing model is pinned
import-free (pure). The wording line now covers four files and rides the
same comment-stripping discipline established in P4 (a KDoc quoting a banned
word can never trip the pin).
