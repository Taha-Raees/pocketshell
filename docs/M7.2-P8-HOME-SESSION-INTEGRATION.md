# M7.2 P8 — Home Sessions Integration & Unified Agent Activity

Phase: M7.2 P8 (consumer/UI integration phase) · Date: 2026-09-09 ·
Baseline: `40cf81e` (the P7 tip `326ee2a` + one zero-implementation
delivery-record ride-along) · Version: versionCode 47 /
`0.11.2-m7.1.1` (unchanged, per the mandate's Part R).

## 1. The one-sentence contract

P8 makes the EXISTING Home → Sessions section state the SAME
authoritative agent activity the notification system already states —
no second discovery path, no second lifecycle owner, no new state
machine — so the shade and the session rows are two views of one
runtime state, never two independent systems.

P7's verdict stands untouched: generic "Needs input" cannot currently
be claimed truthfully, and P8 does not attempt to revive it. P8's
product is a *consumer*: it reads the same two authorities P3c/P4
already consume (the manager's session state, the detector's graded
observations) and decides, in one pure step, what a session row may
honestly say.

## 2. The existing Home Sessions architecture (Part B audit)

Home is drawn by `HomeScreen` (`ui/home/HomeScreen.kt`, the Phase 3.3
OS-home canvas: IDENTITY / FOUNDATION / FILES / COMPANIONS / TOOLS /
SESSIONS / floating control — none of which P8 redesigns). The
Sessions section is `SessionsSection`, a flat list of continuation
rows between hairline dividers, capped at four rows plus a
"+N more in Terminal" line. Before P8 each row showed:

    [8dp dot]  <displayLabel> (exited when finished)   #<id>

- the dot: green when the session's DIRECT child is alive
  (`!isFinished`), hairline when finished — a SESSION fact;
- the label: `title ?: label` — the spawn label (the launcher's
  display name for agent launches) unless a terminal title overrode
  it;
- `#id`: the manager's authoritative, monotonic, never-reused id.

How Home knows about sessions: `PocketShellRoot` collects
`TerminalViewModel.sessions` (a pass-through of
`TerminalSessionManager.sessions`, the ONE lifecycle authority) with
`collectAsStateWithLifecycle` and passes the list down. Selection is
the existing seam only: the row tap calls `onOpenSession(id)` →
`terminalViewModel.select(id)` → the terminal screen. Home has never
had a close affordance, a session manager, or any /proc access.

What was already available and P8 consumes (no new seam was needed):

| Authority | Already exposed by |
|---|---|
| Session list + typed lifecycle | `TerminalSessionManager.sessions` |
| Spawn identity per session | `SessionEntry.origin` + `SessionEntry.agent` → `LaunchIdentity.of` (P3a) |
| Graded runtime evidence | `RuntimeAgentDetector.observations` (P3b, the four-state `AgentRuntimeState`) |
| Derived read model | `AgentActivityRepository` (P2/P3a/P3b projections) |
| Notification truth | P3c events → P4 mapping (wordings, cancels, exit facts) |

## 3. The integration seam (Part C — the smallest existing one)

P8 adds exactly one pure projection plus one UI consumer:

    TerminalSessionManager.sessions ─┐
                                     ├─ combine ─→ AgentHomeSessionClaims.present (PURE)
    RuntimeAgentDetector.observations ┘                 │
                                                        ▼
                 AgentActivityRepository.homeSessionClaims  (the ONE derived read model
                                                        │    gains its P8 projection)
                 TerminalViewModel.homeSessionClaims  (read-only pass-through)
                                                        │
                 HomeScreen (collectAsStateWithLifecycle, lifecycle-aware)
                                                        │
                 SessionsSection row: compact status line

- `AgentHomeSessionClaims` (`terminal/AgentHomeSessionClaims.kt`) is a
  PURE decision object: data in, map of claims out; it stores nothing,
  scans nothing, owns nothing. It references the runtime vocabulary as
  the third ROADMAP-authorized consumer (after the repository
  projection and the P3c event engine) — a fact now pinned in
  `LaunchIdentityIntegrationTest`'s vocabulary-confinement allowlist.
- `AgentActivityRepository.homeSessionClaims` is a cold
  `Flow<Map<Long, SessionClaim>>` = `combine(sessions, observations)`
  through the pure step, `distinctUntilChanged`. No polling, no
  timers, no coroutines of its own: it advances only when one of the
  two StateFlows advances.
- `TerminalViewModel.homeSessionClaims` re-exposes the flow verbatim
  (the established delegation pattern of `sessions`/`creating`).
- `HomeScreen` collects it with `collectAsStateWithLifecycle` — the
  collector lives exactly as long as the Home composition and the
  STARTED lifecycle; it produces no side effects on recomposition.

## 4. Session → runtime association (Part F)

A claim can exist ONLY for a session that is

1. LIVE (not FINISHED — the repository filters finished entries out
   before the pure step), and
2. classified `LaunchIdentity.KnownAgent` by the P3a resolver against
   the REAL registry (plain shells have `null` identity; known
   non-agent tools and custom/unknown launchers never claim), and
3. currently observed by the P3b detector with process evidence
   (`RUNNING`), or previously observed and now ambiguous
   (`UNKNOWN` + `everObservedRunning`).

Nothing else can mint a claim: not the launcher having been tapped
before, not the session name, not a recent process sighting outside
the detector, not a command string, not an old notification. When the
runtime evidence disappears (`NOT_RUNNING`), the claim is withdrawn
— the row returns to its normal presentation, exactly as the P4
notification layer CANCELS the running surface. When the session
finishes or its tab is removed, it leaves the live list and the claim
is structurally impossible (the map is keyed by the manager's
authoritative id; a new session inherits nothing).

## 5. The UI state mapping (Part D/E — what Home may show)

`AgentHomeSessionClaims.claimFor(state, everObservedRunning)`:

| Detector state | `everObservedRunning` | Home claim | Row renders |
|---|---|---|---|
| `RUNNING` | true | `RUNNING` | `Kilo Code — Running` (green) |
| `UNKNOWN` | true | `UNKNOWN` | `Kilo Code — Runtime unknown` (dim) |
| `UNKNOWN` | false (birth) | none | normal row (no status line) |
| `NOT_RUNNING` | true | none | normal row — the claim is WITHDRAWN |
| `NOT_APPLICABLE` | — | none | normal row |
| no observation yet | — | none | normal row |
| plain shell / tool / custom | — | none | normal row |
| FINISHED / removed session | — | impossible | existing `(exited)` session fact |

The compact status line is a second `Text` under the row's label —
11sp, single-line, ellipsized; the claim names the agent by its
REGISTRY display name (the same source the P4 wordings use), so the
row stays truthful even when a terminal title overrode the tab
label. The row keeps its identity, its session-level dot, its
`(exited)` suffix and its tap behavior. No badges, dashboards,
progress bars, charts, timers or animations were added.

States Home deliberately CANNOT show: Completed, Success, Failed,
Needs input, Waiting for user — no authoritative source exists for
any of them (P7's verdict; the P0/P3 honesty line before it).

## 6. Multiple-session behavior (Part G)

Claims are keyed by the manager's authoritative session id, and the
pure fold processes every live session independently: shell(1) +
Kilo(2, RUNNING) + Antigravity(3, UNKNOWN) renders three
independent rows; closing the middle session (2) drops exactly its
claim and leaves 1 and 3 untouched; a brand-new session id starts
claim-free even if a stale observation for an old id lingered in a
map (pinned: `a new session receives its own identity and inherits
no stale claim`).

## 7. Process-death behavior (Part J)

Every P8 input is process-scoped in-memory state
(`TerminalSessionManager` sessions, `RuntimeAgentDetector`
observations). After PocketShell process death both are empty, the
claims map is empty, and Home shows only whatever session state the
fresh process genuinely has — no fabricated agent activity, no stale
labels, no session restoration, no notification reconstruction. P8
adds no persistence anywhere (pinned: no File/DataStore/
SharedPreferences in the claim step, the projection, the seam).

## 8. Notification parity (Part I — the contract, and its test)

The gate `everObservedRunning` is what makes Home mirror the P4
surface semantics state-for-state:

| Story step | Notification layer (P4) | Home (P8) |
|---|---|---|
| Launched | nothing | no claim |
| birth UNKNOWN | nothing | no claim |
| ConfirmedRunning | "<Name> is running" | `<Name> — Running` |
| RuntimeUnknown | "<Name> runtime unknown" | `<Name> — Runtime unknown` |
| NoLongerDetected | CANCEL | claim withdrawn |
| SessionEnded (announced) | "Session ended" exit fact | row shows `(exited)`; claim gone |
| SessionEnded (never announced) | nothing | nothing |

`AgentRuntimeHomeParityTest` folds the SAME authoritative input
sequence through the shipped chain (engine → mapping, exactly as the
consumer folds it) and through `present()`, and asserts
`posted RUNNING ⟺ claim RUNNING`, `posted UNKNOWN ⟺ claim UNKNOWN`,
`not posted ⟺ no claim` at every step of: the §55 device story
(spawn → birth-unknown → running → unknown → withdrawal →
reappearance → exit 3 → removal), mixed multi-session worlds with a
middle-session close, the R→U→R→U→R flapping storm, and the
never-announced ending. Home cannot upgrade an UNKNOWN to RUNNING,
cannot keep a claim past a withdrawal, and cannot state anything the
shade would not.

## 9. Rejected designs

- **A Home-level activity dashboard / Running Agents page** — a second
  surface would imply a second discovery model; the mandate forbids
  it and the existing Sessions section is the right place.
- **Collecting `AgentRuntimeEvents` (the event stream) in the UI** —
  events are best-effort edges; a UI that folds events needs its own
  reconciliation memory (a second state machine). The StateFlow
  projection IS the reconciliation authority; the UI reads state, not
  events.
- **Reusing the notification layer's `Memory` (everPosted) in Home** —
  that memory lives in the notification domain; copying it would be a
  second notification system. The equivalent fact
  (`everObservedRunning`) already exists in the detector's
  Observation, one `claimFor` away.
- **Deriving Home state from `runtimeActivities` only** — that
  projection maps a birth-UNKNOWN and an informed-UNKNOWN to the same
  value, which would make Home show "Runtime unknown" where the shade
  is honestly silent (a parity break the mandate's Part I forbids).
- **A tappable status chip with its own navigation** — a second
  navigation mechanism; the row tap already routes to the session.
- **Any "no active agent runtime" banner** — a new section for an
  absence; the normal session presentation IS the honest absence.

## 10. Truth limitations (what P8 does NOT claim)

- Home does not know whether an agent will succeed, fail, or finish —
  the runtime vocabulary stops at NOT_RUNNING and the session layer
  owns endings.
- Home does not read terminal text, does not parse output, does not
  watch files, does not poll, does not scan /proc (the detector it
  reads is the P3b machinery, unchanged).
- Home cannot write to the terminal: the Sessions section gains a
  status line, not a write path (pinned structurally).
- The status line is presentation-only: it changes no routing, no
  session ids, no lifecycle ownership, no notification behavior.

## 11. Why NeedsInput remains excluded

P7 audited every channel (PTY bytes unreachable, stdin untagged with
kernel echo, every structured emulator seam spoofable by a one-line
printf, OSC 133/9;4/777 + APC silently swallowed, no receiver/IPC/
generation concept, launchers bare with zero config staging, exit
status structurally discarded) and concluded no evidence source
satisfies the eight-condition standard. P8 is a consumer of existing
authorities and therefore inherits that boundary: its two claims are
exactly the two the notification layer already makes. Any future
trusted-attention phase must first produce real evidence per the P7
standard, then extend BOTH consumers — the shade and this projection —
through the same pure-step discipline, never one around the other.
