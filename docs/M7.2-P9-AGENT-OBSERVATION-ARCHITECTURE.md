# M7.2 P9 — Universal Agent Activity Detection & the Linux ↔ Android Signal Bridge

**Phase:** M7.2 P9 (investigation + implementation). **Verdict: P9A+B** — the
universal session-bound observation bridge is implemented (discovery), AND the
Linux-side launch-record channel is implemented and connected to the Android
detector. Version stamp unchanged: `versionCode 47 / versionName 0.11.2-m7.1.1`.

---

## 1. The one-sentence contract

Every LIVE guest session's agent activity is now stated from REAL process
evidence — whether the agent was launched by a Home launcher tap or typed by
the user into any terminal session, at any working directory — through the
SAME authorities, the SAME event vocabulary and the SAME notification/Home
surfaces; plus a session-bound launch-record channel (a tiny Linux-side
observer writing structured facts the detector consumes) that anchors the
exact agent pid at exec time and recovers the agent's REAL exit status, which
the architecture has structurally discarded since P2.

## 2. The Part-B audit: the root cause of the Kilo subdirectory discrepancy

The user's real-device observation:

- **PATH 1 (worked):** Home → Kilo Code launcher → agent notification appeared.
  Also: a terminal at "root" → typed Kilo → notification appeared.
- **PATH 2 (broken):** Terminal → `cd <another directory>` → Kilo → only the
  generic "Terminal sessions running" FGS notification, no agent notification.

### 2.1 What actually differs (it is NOT the directory)

The pipeline had ONE gate in front of every consumer — the P3a launch-identity
resolver:

```
TerminalSessionManager.SessionEntry.origin/agent  (spawn-time truth)
        ↓  LaunchIdentity.of(origin, agent)
        ├─ SpawnOrigin.CommandApp(id)   → KnownAgent        (Home launcher taps)
        ├─ SpawnOrigin.LinuxShell       → null              (plain Terminal)
        ├─ SpawnOrigin.FilesTerminal    → null              (Open Terminal Here)
        ├─ SpawnOrigin.CatalogApp(id)   → KnownNonAgentTool (nano/vim/…)
        └─ SpawnOrigin.CustomTool(id)   → CustomOrUnknown   (user tools)
```

Every consumer gated on `KnownAgent` exactly:

- `RuntimeAgentDetector.eligibleSessions` — the /proc scanner never ran for
  any session whose identity was not `KnownAgent`;
- `AgentRuntimeEventEngine.liveAgentLaunches` — no events for the rest;
- `AgentActivityRepository.runtimeActivities` — plain sessions absent;
- `AgentHomeSessionClaims.present` — plain sessions claim nothing.

Therefore: an agent typed into a **plain Terminal session** (opened via "Linux
Shell" or "+") was structurally invisible — no scan, no observations, no
events, no notification — at ANY directory, including `/`. The "directory"
in PATH 2 was a confound: what actually differed is WHICH SESSION KIND the
command ran in. The "works at root" path (PATH 1b) is the **launcher-born
session's post-agent prompt** (`exec /bin/sh -l` leaves the session sitting
at `/root` — "root"): that session KEEPS its `SpawnOrigin.CommandApp` spawn
identity forever (spawn-time truth never changes), so a re-typed `kilo` there
was scanned and detected via the ppid-chain correlation (which is
cwd-independent).

This is code-proven (the P9 audit), reproduced on real Linux with real
process trees (scripts/p9_proc_prototype.sh — 21/21; the topology test
`AgentObservationTopologyTest` pins it permanently against REAL /proc), and
its fix is device-gated as §58-B.

### 2.2 The residual the device gate discriminates

A second-order mechanism — process-SHAPE differences when the resolved binary
differs between directories (e.g. a project-local wrapper re-exec'ing into an
interpreter child, then the parent exiting: the double-escape shape, P3b
experiment E4b) — cannot be fully excluded without the device. §58-B's
logcat evidence lines (`AgentRuntimeDetector`, `AgentRuntimeEvents`) will
show which arm fires on hardware. Both classes are covered by the P9 fix:
discovery sees the typed agent regardless of shape, and the launch-record
anchor names the exact exec'd pid for every registry launch.

## 4. The chosen architecture

```
                       Android (Kotlin)                      Linux guest (Alpine)
 ┌───────────────────────────────────────────────┐   ┌─────────────────────────────────────┐
 │ TerminalSessionManager (the ONE authority)    │   │ launch chain (composed at spawn):   │
 │  SessionEntry{origin, agent, shellPid,        │   │  sh -c 'record pid/pgrp/start;      │
 │              launchRecordPath}                │   │          exec <agent>'              │
 │        │ fork signal → shellPid               │   │  record $? (the REAL exit status)   │
 │        ▼                                      │   │  exec /bin/sh -l                    │
 │ RuntimeAgentDetector (2s tick, parked when    │   │        │ appends JSONL              │
 │   no eligible session)                        │   │        ▼                            │
 │  eligibleSessions:                            │   │  <rootfs>/var/lib/pocketshell-agent/│
 │   PREDICTED (KnownAgent, own token)           │◄──┤    <token>.jsonl  (the SAME file,   │
 │   DISCOVERED (every other live guest session, │   │   the app reads its own fs —        │
 │     whole-registry token scan)                │   │   no bind, no daemon)               │
 │  + launch-record ANCHOR (pid+starttime)       │   └─────────────────────────────────────┘
 │        ▼ compute (PURE)                       │
 │  Observation{state, evidence, agent, lastExit}│
 │        ▼                                      │
 │ AgentRuntimeEventEngine → P3c events          │
 │        ▼                                      │
 │ NotificationCoordinator (P4) / P5 / P6        │   UNCHANGED surfaces
 │ AgentActivityRepository → Home claims (P8)    │   (one state, two views)
 └───────────────────────────────────────────────┘
```

### 4.1 Discovery (the Part-B fix)

- Every LIVE guest session (`origin != Shell`) is eligible: registry-launcher
  sessions keep their spawn-truth token (**PREDICTED**); every other live
  guest session — plain shells, Open-Terminal-Here, catalog tools, custom
  tools — is scanned against the WHOLE registry token set (**DISCOVERED**).
- A match RESOLVES the agent: the claim names the REGISTRY entry the process
  evidence actually found (`Observation.agent`), never the session's label or
  terminal title. Exact-token rules unchanged (no substring matching; the
  chain-shell argv cannot hit).
- Host-side plain shells stay excluded (no guest tree, no agent binaries).
- Spawn truth keeps precedence: a session with a launch identity claims its
  own agent name; discovery never overrides it.
- The engine lazily tracks discovered sessions at their FIRST resolved
  evidence (no invented `Launched` — no launcher named the command); the
  first RUNNING emits `ConfirmedRunning(from=null)` — the birth shape the P4
  mapping already handles. An identity switch (kilo → claude in one session)
  withdraws the old RUNNING claim first, then starts the new agent's story.

### 4.2 The launch-record channel (the Linux ↔ Android bridge)

- **Composition** (pure, pinned): the registry launch chain becomes
  `sh -c '<record pid/pgrp/starttime>; exec <agent>' ; <record exit $?> ; exec /bin/sh -l`.
  One extra short-lived `sh` fork per launch, exec'd immediately — no extra
  VISIBLE process, terminal semantics byte-identical (prototype E1/E3, the
  execution fixtures).
- **The anchor**: exec preserves pid/pgrp/starttime (prototype-proven), so
  the record names THE agent's live process identity. The detector validates
  pid + /proc starttime (the kernel's pid-reuse-proof birth stamp) INSIDE the
  session's correlation domain — a forged or cross-session record cannot
  claim a foreign process (PART T). Grade `LAUNCH_ANCHOR` (strongest) fires
  when exe/cmdline are unreadable; when a token also speaks, the anchor
  corroborates the exact pid inside the evidence.
- **The exit FACT**: the chain records the agent's REAL exit status — P2's
  truth-loss point 3, restored. It rides `Observation.lastExit` as a FACT.
  NO consumer maps it to success/failure/completion (PART P: exit 0 ≠
  success; the P0 rejected tiers stand; the notification vocabulary is
  UNCHANGED in P9).
- **Generation / stale state** (PART O): the file is created FRESH per
  launch tap, named by a random hex token — the file's existence IS the
  runtime generation. A late event from run #1 cannot modify run #2: run #2
  has a different file. closeSession deletes the file; 24h-stale orphans are
  swept at spawn (an mtime comparison, never a timer). Typed relaunches in a
  session carry no records — the tree correlation is live kernel truth, with
  no staleness surface at all.
- **Security** (PART T): the file lives under the app's private storage
  (other apps cannot reach it). Guest processes share the app UID and could
  append to their OWN session's file — the same trust boundary as the
  terminal itself (P7's model); the parser accepts exactly the two record
  shapes, the anchor is validated against live /proc AND the session's own
  tree, and a spoofed record adds nothing discovery does not already see.

## 5. The evidence model (Parts N, M)

Hierarchy, strongest first (each observation names how it was established):

1. `LAUNCH_ANCHOR` — the session's own launch channel named the exact pid,
   and the live snapshot confirms pid + birth stamp in the session's tree.
2. `PROCFS_EXE` — the executable image's basename equals the token.
3. `PROCFS_CMDLINE` — an exact argv element equals the token (shebang
   contract: the script path rides argv[1]).
4. Spawn metadata (`LAUNCH_METADATA`) — what the session was launched AS
   (never a running claim by itself).

The dynamic state model (PART M) is documented, not invented: RuntimePresence
{Unknown, Running, Absent} is what the pipeline states today (unchanged four-
state contract); Activity {Active, Idle, AttentionRequired, Completed, Failed}
has NO evidence source yet — exit status is a FACT (recorded), not an
interpretation, and every "idle/waiting/completed" inference remains
forbidden. The state model admits richer future evidence without corrupting
the P3c meanings (the reducer's vocabulary is unchanged — pinned by test).

## 6. Rejected approaches (PART U discipline)

- **Scanning /proc for ANY agent-like process without session binding** —
  loses the anti-false-positive core; unrelated same-name processes must
  never claim. Correlation stays mandatory.
- **A Linux-side daemon or polling loop** — PART S forbids it; the chain
  observer writes at launch/exit (two events), the detector's existing gated
  2s tick is the only scan.
- **A proot bind for the event channel** — unnecessary: the rootfs IS the
  app's own filesystem; a direct read is simpler and mount-isolation adds
  nothing once the anchor is tree-constrained.
- **Anchors outside the correlation domain** — would open a cross-session
  spoof window (a guest process forging another session's record naming a
  foreign pid); refused.
- **Wrapping custom tools** — an arbitrary user shell line cannot be exec'd
  by the anchor without changing semantics; custom tools keep the verbatim
  chain (discovery still sees their processes).
- **Mapping exit status to Completed/Failed** — PART P's hard line.
- **Title/output-text based detection** — spoofable by a one-line printf
  (P7), forbidden.
- **Kilo-specific detection** — the architecture is registry-generic; Kilo
  is merely the primary device-gate target (PART L).

## 7. Truth limitations (stated plainly)

- **Technically solvable, not implemented yet:** agent-specific adapters
  (Claude Code hooks / Codex notify / OpenCode plugins) — the channel now
  provides per-session binding, generation and the receiver seam; an adapter
  phase stages agent config and writes normalized events. Waiting-for-user
  and completion semantics ride exactly this path. The tagged input door
  (which action wrote to the PTY) is an additive overload away.
- **No known evidence source:** generic "waiting for user" (P7's verdict —
  unchanged); "output = working" (PART I: bytes are produced by everything);
  completion from exit codes or absence.
- **The double-escape blind spot** (P3b E4b) stands for TYPED relaunches:
  an agent that forks a child, exits, and whose child both reparents AND
  leaves the process group is invisible to tree correlation and carries no
  record. Registry launches are anchored (the anchor pid is a direct child
  of the chain shell — its chain cannot break while the agent lives).
