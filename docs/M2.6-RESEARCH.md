# M2.6 Research — Linux Compatibility Recovery, /proc Architecture, apk fd-link Patch

Status: CHOSEN ARCHITECTURE IMPLEMENTED (v0.6.0-m2.6) · Date: 2026-09-02
Baseline: v0.5.0-m2.5 (commit 9baf3b0, versionCode 13) · 281 tests/variant, 562 executions, 0 failures

---

## 1. Problem

v0.5.0 made the interactive Alpine guest apk-capable by removing the `/proc`
bind from **every** guest session. The package manager worked; the Linux
environment regressed: with no procfs in the guest, `ps` has no process table,
`top`/`htop` cannot run, and anything else that reads `/proc` fails. That
directly conflicts with the product requirements (real `bash sh python ssh git
vim nano less top htop tmux` compatibility) and with the Golden Rule: PocketShell
must not trade one Linux feature for another.

M2.6 must restore `/proc` to interactive sessions **and** keep `apk update /
search / add / del` working in the same sessions and from the app UI, with no
fake behavior anywhere.

## 2. Root cause — exact mechanism (primary-source verified)

The device evidence (v0.4.0–v0.4.2, Samsung SM-F711B) showed apk dying with
`Permission denied` while index/package bytes clearly flowed. Source-level
verification of apk-tools (3.0.6 from the pinned Alpine 3.24.1 rootfs; 3.0.8
upstream tag; `src/io.c` byte-identical between them, checked against
upstream `master` on 2026-09-02):

```c
static bool is_proc_fd_ok(void) {
    static int res;
    if (!res) res = 1 + (access("/proc/self/fd", F_OK) == 0 ? true : false);
    return res - 1;
}
```

1. `__apk_ostream_to_file()` (src/io.c): if `is_proc_fd_ok()` → download into
   an anonymous `O_TMPFILE` file; else → named `file.tmp.N` + later `renameat`.
2. `fdo_close()` (src/io.c): the O_TMPFILE branch commits with
   `linkat(AT_FDCWD, "/proc/self/fd/N", atfd, tmpname, AT_SYMLINK_FOLLOW)`.
   It retries **only on EEXIST**; any other errno → `apk_ostream_cancel(-errno)`
   → the whole download (APKINDEX or package) is cancelled. **No fallback.**
3. Android kernel/SELinux: AOSP `system/sepolicy` `app_neverallows.te` —
   `neverallow all_untrusted_apps file_type:file link;` (re-verified in the
   archived policy dumps from the M2.4 investigation: `scratch/app_neverallows.te`,
   `scratch/untrusted_app_27.te`). Apps deliberately keep create/rename/unlink
   on their own data — `create_file_perms` has no `link` — so a procfs-backed
   hardlink is a kernel-enforced EACCES for every untrusted app domain.

Consequences (all device-observed):
- `/proc` visible + stock apk → O_TMPFILE+linkat commit → EACCES →
  "updating and opening …APKINDEX.tar.gz: Permission denied" (v0.4.0/v0.4.1 and
  the v0.5.0 in-shell failure).
- `/proc` absent → `access("/proc/self/fd")` fails → named-tmpfile + `renameat`
  commit → create/rename/unlink, fully allowed → apk works (v0.4.2+ app side,
  v0.5.0 sessions).

The decision is made by an **existence probe** (`access`), not by capability:
there is no errno under which the fd-link path falls back to renameat, and no
mount trick can both keep a real procfs visible and hide `/proc/self/fd` from
that probe (binding a mask directory over `/proc/self/fd` still satisfies
`access(F_OK)`; the subsequent linkat then fails with ENOENT — same cancel).
Masking `/proc/self` (or all of `/proc`) trades real compatibility (process
substitution, `/proc/self/*` readers, musl ttyname probing) for apk's benefit —
exactly the trade M2.6 forbids.

Why apk needs `/proc/self/fd` at all: the fd-link is an atomic-commit
optimization — link an already-open, checksummed download into its final name
without re-opening by path. Script execution (src/database.c
`apk_db_run_script`) also builds `/proc/self/fd/N` paths when an fd is passed
to the interpreter, but that is a plain *read* of the process's own fds and is
allowed for untrusted apps.

## 3. Options evaluated

| Option | Summary | Verdict |
|---|---|---|
| A. Full `/proc`, stock apk | One profile; ps/top work; apk add/update cancel at commit (EACCES, no fallback) | REJECTED — breaks package management (device-proven) |
| B. No `/proc` (v0.5.0) | apk works; ps/top broken | REJECTED — breaks Linux compatibility (the M2.6 complaint) |
| C. Two profiles, no bridge | Sessions with `/proc`, package ops without; in-shell `apk` still fails (it runs inside the `/proc` session) | REJECTED alone — user explicitly requires working in-shell `apk` |
| D1. Two profiles + transport wrapper | Guest `/sbin/apk` wrapper streams argv over an inherited fd to the Android side, which runs the real apk in a no-`/proc` proot and streams stdout/stderr/exit code back | REJECTED — real but heavy: new IPC protocol, executor lifecycle, cancellation, apk progress degenerates to non-tty output; all complexity to work around one probe |
| D2. Nested proot re-exec | Wrapper execs the parent proot (`/proc/ppid/exe`) with modified argv | REJECTED — nested ptrace between the outer/inner proot tracers is fragile, cmdline surgery is brittle, double-trace races on tracee attachment |
| E. Disable the fd-link path in the guest's apk (CHOSEN) | One-byte, checksum-pinned patch to Alpine's own `libapk.so.3.0.0` makes `is_proc_fd_ok()` permanently false → apk always commits via named-tmpfile + `renameat` (the device-proven path) → `/proc` can stay bound in interactive sessions | **CHOSEN** |
| G. Mask `/proc/self/fd` via bind | Only masks the literal self-path; probe still succeeds (mask dir exists) or `/proc/self` masking breaks other features | REJECTED — either ineffective or a new compatibility trade |
| apk-tools 2.x rollback | apk 2 has no fd-link path | REJECTED — cannot read Alpine 3.24 v3 indexes/database; version mismatch with the pinned rootfs |

Upstream check (2026-09-02): apk-tools `master`, `v3.0.8`, `v3.0.7` `src/io.c`
are byte-identical to 3.0.6 — no upstream fallback exists; Termux does not
package apk-tools (still apt-based); Termux/UserLAnd-style Alpine environments
either predate apk 3 or run without the Android link restriction.

## 4. Chosen architecture

**One real apk, one patched byte, two explicit profiles.**

### 4.1 The guest apk patch (GuestApkCompat)

Target: `usr/lib/libapk.so.3.0.0` inside the pinned rootfs — Alpine 3.24.1
aarch64, apk-tools 3.0.6-r0. The library carries exactly two `/proc/self/fd`
literals: the `"/proc/self/fd/%d"` format string (script execution — untouched)
and the standalone `"/proc/self/fd"` gate literal. Disassembly (NDK r28b
llvm-objdump) shows **exactly one** code reference to the gate literal:

```
aarch64 252c4: adrp x0, 0x38000 ; add x0, x0, #0x287 ; bl access@plt ; cbnz w0 …
x86_64  21303: leaq 0x121fc(%rip), %rdi  # 0x33506 ; callq *… ; testl %eax, %eax
```

The patch flips the gate literal's last byte: `"/proc/self/fd"` →
`"/proc/self/fX"` (same length, in place). `access()` then always fails with
ENOENT → `is_proc_fd_ok()` is permanently false → the O_TMPFILE+linkat branch
is compiled-in but never taken → **every** apk write (APKINDEX, package
payloads, database) uses the named-tmpfile + `renameat` path that is allowed
and already device-proven. Nothing else changes: same binary version
(3.0.6-r0), same `apk --version`, same downloads, same output, same exit codes,
same database format. The patched binary is still Alpine's apk — this is a
pinned compatibility micro-patch in the same spirit as the proot micro-patches,
not a fork and not a simulation. Reproducible via `scripts/patch_apk_fdlink.py`
(evidence chain + hashes in the header).

Pins (sha256):
- aarch64 original `ef1c9d8d7337d0a3c30cd0bb795c005d92be5a6ca4fae346fd6155a233780db4`
- aarch64 patched `b8cd95e2c59735594011654dbb5032bbe4fbc14500aa36ec020d7871c0846de9`
- x86_64 original `51ee6652a1a1f36c83edb6fc425882d62c8d074a1ced144b85a961360919189c`
- x86_64 patched `d4410cec28a8bfda7d278ab17ff774b679ce4f2529b0894224f562721ace7f55`
  (x86_64 is rehearsal-only; the app ships the aarch64 asset).

Evaluated alternative within E: shipping a patched `apk-tools-static` 3.0.8
(`/sbin/apk.static`, zero lib deps) instead. Works identically (same literal
layout, verified) but replaces a package-owned file with a different version;
the in-place library patch is more surgical and version-exact. The static
artifacts remain in `scratch/m26/patched/` as documented fallbacks.

### 4.2 Guest execution profiles (GuestExecutionProfile)

`RuntimeProcessLauncher` now models the two launch policies explicitly
(same builder, same proot, same launcher — configuration only, no duplicated
runtime):

- `INTERACTIVE_TERMINAL` — Linux Shell and catalog-app sessions. Binds
  `/dev`, `/sys`, the shared apk cache, **and `/proc` when the guest apk is
  fd-link-safe** (`GuestApkCompat.ensure()` reports the patched library
  verified). Without that verification the session falls back to the v0.5.0
  shape (no `/proc`) — honest degradation, apk still works, ps/top fail with
  their own errors, diagnostics explains why.
- `PACKAGE_OPERATION` — every app-side apk exec (update/search/add/del/info).
  Minimal mounts (`/dev`, `/sys`, shared cache), **never** `/proc` — enforced
  in the builder (`require`), pinned by tests, so this profile cannot drift.

Both profiles share the same rootfs, the same host-side apk cache binds, the
same environment base — one cache, one database, one truth. apk's own locking
serializes concurrent UI + in-shell package operations.

### 4.3 Expected process semantics (documented, not faked)

With `/proc` bound, the guest sees the Android host procfs filtered by the
kernel's `hidepid=2,gid=3009` mount options: only processes owned by the app's
uid are visible. `ps` therefore lists the app's real process tree (guest shell,
nano, top, app-side helpers) with host pids; `top` reads the real
`/proc/stat`, `/proc/meminfo`, `uptime` (system-wide values, honestly
rendered). This is the "subject to Android process isolation" semantics the
product requirements pre-approve. What is not acceptable — `ps` failing
because `/proc` does not exist — is gone.

### 4.4 Wiring

- `PackageGateway.prepareGuestForSession()` now also runs
  `GuestApkCompat.ensure()` (best-effort) and returns its result;
  `TerminalSessionManager` derives `procEnabled` from it when building the
  session spec.
- `AlpinePackageManager.runApk()` runs the same ensure (best-effort) before
  package operations, so the patch is installed even if the user's first
  action is an Explore install; package specs stay `PACKAGE_OPERATION`.
- `GuestApkCompat.ensure()` is hash-driven and idempotent:
  - current == patched pin → Ready (no write);
  - current == original pin → verify the embedded asset against the patched
    pin, install via temp-file + rename, chmod 0755 → Ready;
  - anything else (e.g. an in-guest `apk upgrade` replaced the library) →
    NotApplicable — the file is never touched, the honest reason surfaces in
    Diagnostics, and sessions degrade to the no-`/proc` shape until the user
    reinstalls the runtime from Diagnostics (restoring the pinned rootfs).
- Diagnostics ("Check package environment") reports the fd-link patch status
  read-only (hash, no install) plus the interactive profile's `/proc` policy.

## 5. Risks

1. **Patch fragility across versions** — mitigated: the rootfs is pinned
   (RuntimePin), the library pin is exact, and any drift is detected by hash
   and handled honestly (never half-patched, never silently).
2. **In-guest `apk upgrade` overwrites libapk** → hash mismatch →
   NotApplicable → sessions degrade to no-`/proc` (apk still works — it would
   be the repo's unpatched apk running without `/proc`) + Diagnostics says
   exactly that; reinstalling the runtime restores the pinned state.
3. **SELinux policy variation across OEMs** — the patch does not depend on any
   allow rule being present; it removes the denied operation entirely.
4. **Script execution paths** (`/proc/self/fd/N` reads) remain stock apk
   behavior with `/proc` available; if some OEM denied procfs *reads* of own
   fds, package scripts would fail — not observed on the gate device; honest
   stderr would surface it.
5. **Binary-patch honesty** — the change is one byte inside a documented,
   checksum-pinned, reproducible script; the behavioral equivalent source
   patch is `#ifdef HAVE_O_TMPFILE` compile-out (upstream-reasonable); every
   claim above is verifiable from the disassembly evidence.

## 6. Device gate mapping

- Gate A `/proc` (`ls /proc`, `cat /proc/version`, `cat /proc/meminfo`) →
  INTERACTIVE_TERMINAL with `procEnabled=true`.
  DEVICE RESULT 2026-09-02 (SM-F711B): architecture confirmed — patch
  `applied`, /proc bound, `cat /proc/meminfo` real, pid dirs visible. `ls
  /proc` shows EACCES for kernel-internal nodes and `cat /proc/version` is
  denied (OEM policy denies untrusted_app read on proc_version at
  targetSdk 28) — exactly the §5 risk 3 class; documented as expected in
  docs/TESTING.md §10 "Expected on-device", gate re-anchored to the
  readable tail + meminfo/cpuinfo, `uname -a` for the banner. Synthesizing
  /proc/version was rejected (no-fake rule).
- Gate B process tools (`ps`, `top`) → real procfs, app-uid visibility (§4.3).
- Gate C package manager (`apk update`, `apk search nodejs`) → patched apk in
  either profile.
- Gate D Node (`apk add nodejs npm`, `node index.js`) → unchanged M2.5 flow.
- Gate E app-side installation → unchanged M2.5 flow (`PACKAGE_OPERATION`).
- Gate F interactive CLI (`nano`, `top`, `htop`) → full PTY stack unchanged.
- Gate G session isolation → package ops run in their own proot process
  (`PACKAGE_OPERATION`); apk's lock serializes database access.
