## 1. The one-sentence contract

PocketShell can notify the user when an agent/runtime becomes genuinely confirmed
running, stops being detected, becomes unknown, or its terminal session ends — using
ONLY evidence already available in the P2/P3 architecture — **and this phase posts
Android notifications: it is the first user-visible M7.2 phase**, while remaining
structurally unable to claim that an agent completed, succeeded, failed, or finished
any work (the P0 honesty line, preserved at the wording level and pinned over the
actual shipped strings).

P4 is exactly one arrow: **authoritative runtime events → honest Android
notifications.** It adds no detection, no polling, no lifecycle authority, no
permission machinery, no heuristics, and no new claim about any agent.

## 2. The truth contract (event → notification mapping)

The mapping lives in ONE pure file — `AgentRuntimeNotificationMapping` (no Android,
no coroutine, no clock) — so the whole honesty surface is exhaustively JVM-tested
(`AgentRuntimeNotificationMappingTest`, 23 tests). The matrix:

| P3c event | Notification behavior | Exact honest wording |
|---|---|---|
| `Launched` | **Nothing** | A spawn fact makes no runtime claim; the FGS "Terminal sessions" notification already covers session existence. Posting per launch would be noise. |
| `ConfirmedRunning` | Post/update the per-session **ongoing state surface** | Title: `<RegistryDisplayName> is running` · Body: `Agent process confirmed in terminal session N` |
| `RuntimeUnknown` | Update the same surface in place | Title: `<Name> runtime unknown` · Body: `Runtime state cannot be verified right now (session N)` |
| `NoLongerDetected` | **Cancel** the surface | No replacement notification. Runtime disappearance is NOT completion — the honest representation of "no longer detected" is the ABSENCE of the running claim. |
| `SessionEnded` (SESSION_FINISHED, exit status present, session had ever been announced) | Replace the surface with a **one-shot exit fact** | Title: `Session ended` · Body: `Terminal session N exited (code X)` / `Terminal session N was terminated by signal Y` |
| `SessionEnded` (otherwise: SESSION_REMOVED, or the session was never announced) | **Cancel** the surface if one exists; otherwise nothing | A user-removed tab is user-known; a never-announced session gets no end-of-story notification. |

Wording rules (each pinned by test):

- **Display names are never invented**: the title uses
  `LaunchIdentity.KnownAgent.displayName` — the launcher REGISTRY's own name (the
  only name genuinely known). There is no "unknown display name" case: the event
  vocabulary guarantees a resolved `KnownAgent` identity.
- **"No longer detected" is never re-labeled**: no produced string contains
  completed/success/finished/failed; the pinned honesty sweep folds a full session
  story (launch → confirm → unknown → recover → disappear → reappear → end) and
  checks every produced string.
- **The exit statement stays session/process-scoped**: `Session ended` /
  `Terminal session N exited (code X)` — the DIRECT CHILD's waitpid status,
  preserved verbatim and uninterpreted. Exit code 0 is never converted into agent
  success/completion wording (pinned explicitly with `Exited(0)`).
- **Unknown stays unknown**: the unknown surface says "cannot be verified"; it
  never degrades into "not running" and never dresses up as any other state.

Deliberately silent arms (documented, not forgotten): `Launched` (no runtime claim);
`NoLongerDetected` (absence IS the honest state); `RuntimeUnknown` for a session
this layer never announced (structurally impossible per the engine's contract —
`RuntimeUnknown` requires an informative prior state, which would have posted a
surface — pinned as defensive silence); `SESSION_FINISHED` for a never-announced
session (no surface, no story, no spam).

## 3. Lifecycle ownership (the mandatory question)

**Where is the correct lifecycle owner for notification consumption? — the
Application process scope** (`PocketShellApp.onCreate`), for reasons that come from
the existing architecture, not preference:

1. **The stream is a replay-free SharedFlow** (P3c Part H): an event emitted before
   subscription is gone. No session can spawn before `Application.onCreate`
   returns, so the single subscription armed at process start can never miss an
   event. This is a correctness argument, not a style choice.
2. **The P1 precedent**: `NotificationCoordinator.init(this)` already runs there;
   the consumer joins the same process-scoped init chain (immediately AFTER the
   coordinator, so the posting path exists before the subscription).
3. **TerminalService is the wrong owner**: its lifecycle tracks session existence
   (starts with the first session, stops when the last one closes) — consumption
   must not be coupled to service restarts; the service is the retention surface,
   not an event consumer.
4. **An activity-scoped owner would tear down collection** on recreation and
   silently miss transitions while gone (replay=0 means no catch-up).

No second lifecycle engine exists: the consumer holds only a notification-domain
memory (what surfaces IT showed — §5), never session truth. `TerminalSessionManager`
remains the ONE lifecycle authority; `RuntimeAgentDetector` the ONLY evidence
producer; `AgentRuntimeEventEngine` the ONLY event producer.

```
AgentRuntimeEventEngine  (P3c — the ONLY event producer; dedup lives there)
        ↓
AgentActivityRepository.agentRuntimeEvents  (the re-exposed stream)
        ↓
AgentRuntimeNotificationConsumer  (the ONE subscriber — Application scope)
        ↓  AgentRuntimeNotificationMapping (PURE truth contract, §2)
NotificationCoordinator  (P1 — the ONE posting/identity/ledger owner)
        ↓
Android notification system
```

## 4. Channel architecture (Part D — minimum channels, calm)

One new channel, created by the coordinator (the single owner, idempotently,
beside the P1 channel):

| Channel id | Name | Importance | Carries |
|---|---|---|---|
| `session_events` (P1, unchanged) | Session activity | DEFAULT | P1's session-activity kind (still no production caller) |
| `agent_runtime` (P4) | **Agent activity** | DEFAULT | The per-session runtime state surfaces + the one-shot exit facts |

Calm rules, enforced in the builder:

- **The per-session surface updates in place** across state changes (one
  notification id per session — §5): confirmed-running → unknown → running again
  never spawns additional notifications.
- **`setOnlyAlertOnce(true)`**: an in-place update never re-alerts; polling-derived
  transitions (P3b's 2-second tick is upstream of P3c's dedup) can never produce
  sound or vibration spam.
- **`ongoing` surfaces for live state**: the running/unknown surface stands until
  the truth changes it (`NoLongerDetected`/`SessionEnded`), not until the user taps
  it. One-shot facts (the exit statement) auto-cancel on tap.
- The FGS channel `terminal_sessions` (TerminalService, id 1) is untouched and
  separate (§7).

No channel bloat: two event channels total; any further channel requires a
genuinely new event class.

## 5. Notification identity and deduplication (Part G)

**Identity**: `NotificationIds.agentRuntime(sessionId) = AGENT_RUNTIME_BASE + sessionId`
(base 20_000, above the P1 event space at 10_000 and the FGS id 1). Deterministic
(same session → same id → update/cancel-in-place), stable across calls, never
hash-based, never random, never derived from a display string (the event's typed
`KnownAgent` identity is the source; the id comes from the manager's monotonic
session id). Out-of-range session ids fail loudly instead of wrapping silently
(pinned).

**Deduplication, defensively** (without a second event state machine): P3c already
emits every state change exactly once; the notification layer adds its own
per-session in-memory guard so the guarantee does not depend on upstream
perfection:

- `posted` (session → surface kind): a repeated identical surface is a **no-op**
  (three `ConfirmedRunning` deliveries = one notification);
- `everPosted` (sessions ever announced): gates the exit fact — no end-of-story
  notification for a session whose runtime was never shown;
- `ended` (tombstones): an event arriving for an ended session is refused outright —
  a late or duplicate delivery can never resurrect a surface.

All three live in the consumer, guarded by its ONE sequential collector (the
engine's memory discipline), process-scoped, bounded by the number of agent
sessions the process saw. Collector restart in-process cannot re-fire (replay=0);
process death clears the memory AND the sessions (nothing is restored — §8).

## 6. Permission boundary (Part E — audit result, no new machinery)

Audit findings: `targetSdk = 28` (the documented deliberate decision), `compileSdk
= 36`, `minSdk = 26`; `POST_NOTIFICATIONS` **already declared** in the manifest
(since M2.4, for the FGS retention notification); the runtime permission flow
**already exists** since P1 — `NotificationPermissionPolicy` (the pure, JVM-pinned
decision table: pre-13 never asks; granted never asks; this install's one
controlled request is marked spent BEFORE the dialog launches; a system-implicit
denial is respected) and `NotificationPermissionGate` (mounted once at the
composition root, fires only when the FIRST terminal session exists — a
feature-driven moment, never at bare app startup).

**P4 adds zero permission code** — pinned: no permission API appears in either P4
file; the manifest is unchanged (5 declared permissions; the P1-era source pin
still passes). Denial is always safe: `NotificationCoordinator.post` returns false
honestly, the consumer logs it, sessions and the terminal are unaffected.

## 7. The foreground-service regression boundary (Part I)

`TerminalService` is a SEPARATE system, untouched: channel `terminal_sessions`,
notification id 1, IMPORTANCE_LOW, the same start/stop contract
(`syncWithSessionState`: any session exists → service runs with its retention
notification; all sessions gone → service stops → notification disappears). P4
does not replace it, merge it, duplicate its ownership, or reference it from
anywhere in the notification surface — all pinned structurally (the P4 files
contain no `TerminalService`/`terminal_sessions` reference; the service source
keeps its exact constants). The P1-era structural pin
(`TerminalService keeps its own channel and id`) still passes unmodified.

One honest distinction to keep visible: the FGS notification is about SESSION
RETENTION (the service keeping processes alive); the P4 surfaces are about AGENT
RUNTIME STATE (what P2/P3c proved). They can be visible at the same time; they
share nothing.

## 8. Stale notification cleanup (Part J)

| Scenario | What happens | Why it is honest |
|---|---|---|
| Agent running → session closed (SESSION_REMOVED) | Surface cancelled (or replaced by the exit fact if the process had actually finished first) | A surface must not outlive its session |
| Agent running → SESSION_FINISHED (exit) | Surface replaced by the one-shot factual exit statement | The story ends with the session's own fact |
| **App process death** (agent/session existed; PocketShell killed; app restarted) | Nothing is restored. The P1 startup sweep cancels exactly the ledger-recorded ids; sessions are process-scoped and never restored, so the fresh process has NO runtime state to fake — and no `Agent running` notification without proof | The architecture cannot prove the agent still runs after a process death; showing it would be fabrication |
| Detector uncertainty (RUNNING → UNKNOWN) | The surface updates to "runtime unknown" in place | Certainty is not maintained that the evidence no longer supports |
| User swipes the ongoing surface | No repost (no new event; the memory says the surface exists) | Calm over nagging; the state has not changed, so re-announcing would be noise |

The user-swipe arm is a documented trade-off: the layer trusts the user's
dismissal and never re-announces an unchanged state. If a future phase wants
persistent re-surfacing, that is new policy with its own honesty analysis — not
P4.

## 10. What P4 still cannot prove (the honesty ledger, carried forward)

1. **Completion/success/failure of any agent's work** — no notification in this
   phase claims any of it; no event in the P3c vocabulary represents it; no
   wording was added that could.
2. **"No longer detected" = "finished"** — never; the surface is WITHDRAWN, and
   the only statement that may follow is the session's own exit fact.
3. **Exit code 0 = the agent succeeded** — never; the exit statement is about the
   terminal session's direct child (proot), with the code preserved verbatim and
   uninterpreted.
4. **A pre-death running state after a process death** — the architecture cannot
   prove it, so the sweep removes every ledgered surface at startup and nothing
   is re-shown without a new event.
5. **Unknown states stay unknown** — a persistent UNKNOWN (scanner unavailable,
   ambiguity) surfaces as "runtime unknown" or silence, never dressed up; the
   NOT_APPLICABLE class (non-agent launches) never reaches this layer at all.

## 11. Known limitations (honest, each by design)

1. **Delivery is best-effort**: events beyond the 64-event buffer with no keeping-
   up collector are dropped-with-log (P3c's contract); a dropped transition means
   a missed notification, never a wrong one.
2. **No re-announce after user dismissal**: a swiped state surface stays gone
   until the state actually changes (§8).
3. **The exit fact rides the ledger/sweep policy**: a one-shot exit statement that
   outlives the process is cancelled at the next app start, exactly like every
   coordinator-owned notification since P1 — the established stale-notification
   policy was not re-litigated in P4.
4. **No rich content**: plain title/text only — no progress, no output preview, no
   per-agent icons; adding any would need real evidence sources P4 does not have.
5. **One channel for the whole runtime class**: per-agent granularity (a channel
   per agent) is deliberately NOT created — the mandate's anti-bloat rule wins
   until a real need exists.
