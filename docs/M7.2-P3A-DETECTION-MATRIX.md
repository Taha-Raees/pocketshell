# M7.2 P3a — Trusted Agent Signal Audit & Detection Design

**Phase:** audit + narrowly scoped implementation (internal metadata plumbing
only). **Baseline:** the M7.2 P2 record tip (lifecycle engine + structured
exit status shipped, 810/810 JVM green). **No user-visible change, no
notifications, no /proc scanning, no output parsing, no version bump.**

The P2 architecture already answered HOW PocketShell knows a session's
lifecycle (docs/M7.2-P0-AUDIT.md §10.3, `terminal/SessionLifecycle.kt`).
P3a answers the next question honestly:

> What trustworthy evidence can PocketShell obtain that a supported agent
> launched through PocketShell is currently running?

The answer below is derived from the real sources and registries at the P3a
baseline — not assumed from any external list.

---

## 1. The three statements (the core safety rule)

These are NOT interchangeable, and P3a's model deliberately represents only
the first:

| Statement | Evidence PocketShell has | Representable in P3a? |
|---|---|---|
| 1. "PocketShell launched X." | The typed `SpawnOrigin` + `AgentHint` recorded at spawn, before the first byte flows (P2); classified against the real registries (`LaunchIdentity`, new in P3a). | **YES** — `LaunchIdentity` |
| 2. "X is currently running." | **NONE at agent level.** See §2/§3: the direct child is proot; the agent is an invisible descendant; the fork signal fires before the guest shell has executed the command line; the `; exec` chain keeps the direct child alive after the agent exits. | **NO** — no API exists |
| 3. "X completed." | **NONE at agent level.** The agent's own exit status is consumed by the intermediate `sh -l -c` shell (no `$?` capture exists anywhere in the launch chain); session FINISHED + `ExitStatus` is the DIRECT CHILD's exit (the guest session ending), never the agent's completion. | **NO** — no API exists |

Converting statement 1 into statement 2 without real runtime evidence is the
exact lie this milestone forbids. P3a's type system enforces the boundary:
`LaunchIdentity` carries no running/completion/exit field, and a repo-wide
structural test pins that no `isAgentRunning`-style API exists.

## 2. Signal audit — what the architecture can truthfully know

### 2.1 Spawn-origin truth — RELIABLE (Tier 1, P0 PART D Case A)

Every launch path converges on `TerminalSessionManager.spawn` with a typed
origin recorded at spawn time (verified at the P2 spawn sites):
`MainActivity` taps → `openCommandApp`/`openCustomTool` →
`SpawnOrigin.CommandApp(app.id)` / `SpawnOrigin.CustomTool(tool.id)`;
`ExploreAppsScreen` "Open" → `openCatalogApp` → `SpawnOrigin.CatalogApp(entry.id)`;
plus the three shell paths (`Shell` / `LinuxShell` / `FilesTerminal`).
The three named-launcher paths carry `AgentHint(displayName, command,
matchedBy=LAUNCH_METADATA)`. Launcher ids are stable (registry/catalog seed
lists are compile-time constants; custom-tool ids persist in the launchers
DataStore). Session metadata is in-memory only by design — no persistence
was added in P3a.

### 2.2 Child-process truth — session-level only

The real per-session process events are exactly two (P2): the fork signal
(`setTerminalShellPid` → STARTING→RUNNING) and the waiter's `waitpid`
delivery (→FINISHED with structured `ExitStatus`). JNI `waitpid` observes
the PTY's **direct child only** — for guest sessions that is **proot**
(P0 audit §1.3). The agent binary is a descendant of proot and is invisible
to this layer. `/proc` descendant scanning could add real evidence — that is
the P3b scanner phase, explicitly OUT OF SCOPE here (no `/proc` reading, no
polling, no timers were added; pinned by test).

### 2.3 Terminal-session truth — where it is lost

The chain "launched known command → agent process starts → agent remains
active → agent completes" breaks at three precise points:

1. **STARTING→RUNNING proves a fork of proot, not an agent start.** The
   signal fires when the PTY child exists — the guest shell has not yet
   executed the command line, and the agent is a descendant.
2. **Session RUNNING does not imply agent running.** Every named-launcher
   chain is `sh -l -c "<command>; exec <guestShell> -l"` (`guestLaunchChain`
   / `guestCustomCommandChain`): after the agent exits, the exec'd login
   shell keeps the direct child alive. The session is RUNNING at the prompt.
3. **Session FINISHED does not imply agent completion, and the exit status
   is not the agent's.** The `;` sequence discards the agent's exit status;
   the recorded `ExitStatus` is proot's (the whole session ending — e.g. the
   user exiting the post-agent shell).

Therefore "spawned known command" is NOT equivalent to "known agent is
currently running", and P3a does not pretend otherwise.

### 2.4 Explicit integration signals — audited, none implemented

| Candidate | Verdict |
|---|---|
| Command wrappers (e.g. `kilo; echo $? > <file>`) | Potentially trustworthy — but it is a NEW launch contract touching the frozen launch chain; a deliberate future phase, not P3a. |
| Environment-variable handshake (PocketShell already owns the guest env) | Potentially trustworthy with a versioned contract; not available today; not implemented. |
| Exit-status capture | Potentially trustworthy ONLY via the wrapper above (the current chain structurally discards it). |
| Structured stdout protocols / OSC 133 | Untrustworthy to parse at this layer; output parsing is forbidden territory (heuristic class). Rejected. |
| Callbacks / official agent APIs | Not available for any registry agent in this architecture. |
| Local files written by agents (state dirs) | Undocumented, unstable third-party contracts — untrustworthy. Rejected. |

**The custom-tool truth boundary (PART D):** a custom launcher is user
configuration, not an agent claim. `Name: My Agent, Command: python foo.py`
classifies as **CustomOrUnknown** — PocketShell cannot honestly infer
"AI agent running" from a user-chosen name, a user-chosen command, or even
an id/name collision with a registry entry. The classifier resolves custom
tools against NO registry, structurally (pinned by test).

## 4. Detection classification matrix (PART E)

Classes: **A** spawn-identifiable · **B** runtime-confirmable ·
**C** completion-confirmable · **D** unknown beyond the launch claim.
All entries ride identical machinery (same `launchGuestCommand` core, same
proot PTY), so the columns are mechanically identical; per-agent differences
would only appear in P3b's procfs shape, which this phase cannot observe.

| Launcher / tool | A — spawn-identifiable | B — runtime-confirmable | C — completion-confirmable | Evidence source |
|---|---|---|---|---|
| hermes / opencode / claude / zcode / kilo / cline / agy / codex / qwen | **YES** (A) — stable registry id + hint at spawn | **NO** (D) — direct child is proot; agent invisible; `; exec` keeps session alive after agent exit | **NO** (D) at agent level — agent exit status discarded by the chain; session FINISHED is proot's exit, not the agent's | `SpawnOrigin.CommandApp(id)` + `AgentHint(LAUNCH_METADATA)`; P2 lifecycle on the direct child |
| Catalog: nano / htop / vim / git / python3 | **YES** (A) — as known NON-agent tools | **NO** (D) — same machinery | **NO** (D) — same machinery | `SpawnOrigin.CatalogApp(id)` + hint |
| Custom tool | **YES** (A) as "launched user-defined launcher X with command Y" — **never as an agent** | **NO** (D) | **NO** (D) | `SpawnOrigin.CustomTool(id)` + user-supplied name/command |
| Plain shell (Terminal / "+", Linux Shell, Files "Open Terminal Here") | n/a — no launcher named a command; NO identity claimed | Session-level only (P2 truth) | Session-level only (P2 truth) | `SpawnOrigin.Shell/LinuxShell/FilesTerminal`, agent=null |

Session-level rows (P2, unchanged): "the session launched as X is alive at
the direct-child level" and "the session launched as X has ended with status
Y" ARE real, waitpid-proven facts — they are about the SESSION (proot), and
P3a keeps them labeled as session facts.

## 5. Implementation boundary (PART F — what was actually added)

Minimum internal plumbing only, exactly where the audit proves it valid:

- **`terminal/LaunchIdentity.kt`** (new): sealed `LaunchIdentity` with
  `KnownAgent` / `KnownNonAgentTool` / `CustomOrUnknown`, plus the pure
  resolver `of(origin, agent)` — registry-resolved classification, honest
  degradation for unresolvable ids, `null` for plain shells, NO registry
  consultation for custom tools, and NO runtime/completion representation
  (the type system carries the §1 truth rule).
- **`AgentActivityRepository`** (extended): `classifiedLaunches` — a derived
  per-session projection through the classifier. Stores nothing, decides
  nothing, touches no notifications (the P2 read-model contract preserved).
- **Nothing else.** No spawn-site change (P2 origins/hints already record
  the full spawn truth), no manager change (one lifecycle authority, PART
  H), no persistence, no UI, no notifications, no `/proc`.

## 7. What P3a deliberately does NOT do

No notifications (nothing posted, no channels, no actions); no Home/Settings
UI change; no agent-running UI; no completion or waiting-for-input
detection; no `/proc` scanning or process polling; no heuristic inference
from terminal text ("Thinking…", "Done", "Working"); no OSC 133; no custom
tool promoted by its name; no launcher tap upgraded to a running claim; no
version bump (the stamp stays 47 / `0.11.2-m7.1.1`). The runtime-completion
upgrade path remains exactly where the P0 audit left it: P3b's device-verified
procfs descendant scanner, graded `PROCFS_EXE`/`PROCFS_CMDLINE` — added there
as compile-time-forced extensions through the manager, never pre-invented here.
