# M7.2 P10 — The Agent-Native Signal Bridge (research + implementation)

**Phase:** M7.2 P10 (agent laboratory + Linux→Android signal bridge).
**Verdict: IMPLEMENTED** — the three strongest agents (Claude Code, Codex,
OpenCode) are bridged through their own verified notification mechanisms,
with session-bound, generation-safe correlation, feeding the ONE
authoritative activity model. Version stamp unchanged: `versionCode 47 /
versionName 0.11.2-m7.1.1`.

Base commit: `58f39bd` (audit HEAD). Implementation commit: `f55eab7`.

## 1. The one-sentence contract

When an agent ITSELF declares a state through its own structured
notification mechanism (hook / notify / plugin event), PocketShell now
carries that declaration — validated against the session's launch anchor
and live process truth — into the same activity model that already feeds
Home Sessions and the notification shade; where no agent-native signal
exists, the P3b/P9 process truth stands alone, unchanged.

## 2. Why: the P7 conclusion was about OBSERVATION, not about agents

P7 proved: no combination of generic terminal/process observation can
honestly produce "waiting for input" or "completed". P10 does not
contradict that — it changes the EVIDENCE CLASS. The agents themselves
expose exactly those moments as machine-readable events. The mission was
to verify that experimentally and bridge it.

## 3. The agent laboratory (what was actually investigated)

An x86 BunsenLabs laptop was used as the lab; agents were installed into
an isolated prefix (`~/agent-lab`), and each was driven against a LOCAL
MOCK API server (no credentials, no external calls) so a REAL agent
session could complete a REAL turn on the laptop. Raw artifacts: lab
`experiments/{claude-1,codex-1,opencode-1,inspection,emitter-test}`,
mirrored key findings under `docs/p10-lab/`.

### 3.2 The verified payloads (the exact evidence)

**Claude Code — PermissionRequest (interactive session, real dialog):**

```json
{"session_id":"57587d56-…","transcript_path":"…","cwd":"…",
 "prompt_id":"13399bff-…","permission_mode":"default",
 "hook_event_name":"PermissionRequest","tool_name":"Bash",
 "tool_input":{"command":"rm -rf /tmp/ps-lab-target","description":"lab rm"},
 "permission_suggestions":[{"type":"addDirectories","directories":["/tmp"],…}]}
```

**Claude Code — Notification (same moment):**

```json
{"session_id":"57587d56-…","hook_event_name":"Notification",
 "message":"Claude needs your permission","notification_type":"permission_prompt"}
```

**Claude Code — Stop:** adds `"stop_hook_active":false,
"last_assistant_message":"Lab run complete."`. **SessionStart/SessionEnd/
UserPromptSubmit/PreToolUse/PostToolUse** all fired in print mode with the
same session identity. `--settings <file>` hooks MERGE with the user's
real config (both fired; auth untouched).

**Codex — notify (per turn, argv JSON, no trust gate):**

```json
{"type":"agent-turn-complete","thread-id":"01a0afc1-…","turn-id":"01a0afc1-…",
 "cwd":"…","client":"codex_exec","input-messages":["say hi"],
 "last-assistant-message":"Lab run complete."}
```

**Codex — hooks (stdin JSON; `$CODEX_HOME/hooks.json`, `stable` feature):**
SessionStart/UserPromptSubmit/Stop verified live; binary carries
`PermissionRequest/PostToolUse/…` with Claude-style
`permissionDecision` (approve|block|ask). NOT armed by the adapter: a
fresh `CODEX_HOME` triggers per-launch hook-trust prompts — documented
deferral.

**OpenCode — plugin event bus (real permission flow):**

```json
{"id":"evt_…","type":"permission.asked","properties":{"id":"per_…",
 "sessionID":"…","permission":"bash","metadata":{"command":"…"}}}
{"id":"evt_…","type":"session.idle","properties":{"sessionID":"…"}}
```

`permission.replied` fired on resolution; `session.status busy` during
work; the turn ends with `session.idle` exactly once.

### 3.3 The strongest common pattern

Every investigated agent has SOME local hook-shaped mechanism whose
payload is JSON naming the agent session. Three transports exist:
JSON-on-stdin (hooks), JSON-as-argv (Codex notify), in-process plugin API
(OpenCode). All three reduce to ONE bridge shape: a per-launch staged
config points the agent's own mechanism at a tiny emitter that appends a
normalized record to the session's launch-record file. That is exactly
the P9 channel — extended by one record shape.

## 4. The bridge architecture

```text
Layer 1  kernel/process/session truth          (P2/P9 — unchanged)
Layer 2  Linux runtime detection (/proc scan)  (P3b — unchanged)
Layer 3  AGENT-NATIVE SIGNALS                  (P10 — NEW)
           agent's own hook/notify/plugin event
             → staged config (per-launch <token>.d/)
             → assets/agentbridge/ps-emit.sh  (or the staged plugin)
             → {"t":"signal",…} appended to the session's record file
Layer 4  unified activity state                (P3c/P9 — one authority,
           acceptance gate + attention axis     extended, not replaced)
Layer 5  Home Sessions + notification shade    (P4/P5/P8 — same projection,
           two new wordings + turn surface      one authority)
```

### 4.1 What the emitter writes

```json
{"t":"signal","agent":"<token>","kind":"<kind>","seq":<n>,
 "pid":<parent-pid>,"start":<parent-starttime>,"data":"<payload>"}
```

- `kind` vocabulary (fixed, parser-validated): `session_start`, `working`,
  `permission_request`, `attention`, `turn_complete`, `session_end`.
- `data` is the agent's raw payload, single-line, escaped, bounded (≤800
  chars) — moved verbatim, never interpreted on the Linux side.
- `pid`/`start` are the EMITTER'S PARENT at emit time (the agent process)
  with /proc stat field 22 — the pid-reuse-proof identity.
- The emitter is POSIX sh, busybox-safe (dash + busybox verified), O(1)
  in the file size, and structurally incapable of failing the agent
  (every step guarded, always exit 0).

### 4.2 Session correlation (the PART T boundary, carried forward)

A signal speaks for a session ONLY when ALL of these hold
(`AgentSignalBridge.accept`):

1. **GENERATION** — it was parsed from the session's OWN record file
   (the file is the binding; hooks are staged per-launch, so the emitter
   only ever knows this session's file path).
2. **IDENTITY** — the named agent token equals the session's expected
   agent (spawn-truth token, or the anchor's token for discovery).
3. **ORIGIN** — the recorded parent is EITHER the launch anchor (pid +
   birth stamp match) OR a live process with the same birth stamp inside
   the session's correlation domain (ppid-chain ∪ process group).

Recycled pids (different birth stamp), foreign processes (outside the
correlation domain), zombies, wrong tokens, missing anchors + no
snapshot: ALL rejected. A signal can never update another session,
another agent, or another runtime generation — the same structural
guarantees as the P9 anchor, now applied to agent-declared events.

### 4.3 Generation safety

The staging dir `<token>.d/` lives beside the record file and dies with
it (session close deletes both; the orphan sweep now sweeps both). A new
launch tap = new token = new record file + new staging = a new
generation; the detector resets its signal-delivery cursor on anchor
identity change, so late signals from a previous generation are
structurally impossible (their file no longer exists) and a new
generation's signals deliver exactly once.

### 4.4 The attention axis (orthogonal, additive)

The P3b four-state contract (NOT_APPLICABLE/UNKNOWN/NOT_RUNNING/RUNNING)
is UNCHANGED. Signals feed a second, orthogonal axis:

- `AgentAttentionRaised(kind)` — the agent PROVES it waits (permission /
  input). Delivered exactly once per new signal; a genuinely new prompt
  re-raises.
- `AgentAttentionCleared(cause)` — a later signal proves the wait is over
  (resumed work / turn ended / agent session ended), or the process story
  ends (NOT_RUNNING), or the session reaches its terminal edge. Cancel-
  shaped: never a replacement claim.
- `AgentTurnSignalled` — the agent's own turn-end fact, emitted ONLY when
  no attention was pending (a turn that ends a pending attention emits
  the withdrawal alone — one story per signal, no contradictory surfaces).

Engine invariants (pinned by tests): signals fold in append order,
independent of four-state edges; UNKNOWN (ambiguous scan) does NOT
withdraw attention; exactly-once consumption by line index.

### 4.5 The surfaces (one authority, two views)

- **Notification shade** — new `AGENT_ATTENTION` id space
  (`AGENT_ATTENTION_BASE + sessionId`), so "is running" (ongoing fact) and
  "is waiting on you" (action-needed) coexist. Wordings, per the
  documented revision of the P7 ban lists (§6): `"X is requesting
  permission"` (the narrow claim P7 §10 mandated), `"X needs your input"`,
  `"X ended its turn"` (deliberately NOT "finished" — the P4 sweep still
  bans it, and a turn end is not a completion claim). Withdrawals cancel;
  the exit-fact and running surfaces are unchanged. Taps route through the
  same session-targeted `ROUTE_OPEN_SESSION`.
- **Home Sessions** — `Claim` gains `ATTENTION_PERMISSION` /
  `ATTENTION_INPUT` and they OUTRANK process claims (an accepted signal
  carries validated parent identity — the strongest evidence class). The
  wording is exactly the shade's: `"X — Requesting permission"` /
  `"X — Needs your input"`.

## 6. The wording revision (conscious, documented, per P7 §10's requirement)

P7 froze the wording ban lists because no evidence existed. P10 adds the
evidence class P7 demanded (versioned per-agent contract, runtime
generation, app-side receiver — P7 §14's checklist, satisfied in §4). The
revision:

- ALLOWED now, from agent-native evidence only: "is requesting
  permission" (permission evidence), "needs your input" (input evidence),
  "ended its turn" (turn evidence).
- STILL BANNED everywhere: "completed", "success", "finished", "failed",
  "waiting for input" (the P4 string-literal sweep still runs and now
  also pins the new attention wordings; the turn wording deliberately
  avoids "finished").
- Every attention surface can answer "what proved this?" — the exact
  accepted signal record (kind, line index, payload).

## 7. What is now genuinely detectable — and what still is not

**Now detectable (agent-proven, identity-validated):** permission
requests, input waits, turn completion, agent-declared session end, and
the clearing of all attention states (work resumed / turn ended / agent
gone). Multi-agent, multi-session, relaunch-safe, pid-reuse-safe.

**Still impossible (unchanged honesty):** task success/failure (PART P
stands — no consumer maps exit codes or turn ends to success); generic
"waiting" for agents WITHOUT a bridged mechanism; working-vs-idle for
unbridged agents; anything about an agent whose hooks the user disabled
or overrode inside the session.
