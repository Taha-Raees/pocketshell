## 3. Architecture audit — the five questions answered

**Q1. Which P3c transitions are realistically observable on-device today?**

| Transition (event) | On-device trigger | Reproducible? |
|---|---|---|
| `Launched` | every eligible agent session spawn (silent) | YES (§53 proved) |
| `ConfirmedRunning` (birth UNKNOWN→RUNNING) | first 2s scan after an agent appears | YES (§53/§54 proved) |
| `NoLongerDetected` (RUNNING→NOT_RUNNING) | quit the agent INSIDE a still-live session (shell prompt returns, tab stays) | YES — natural, deterministic |
| `ConfirmedRunning` reappearance (NOT_RUNNING→RUNNING) | relaunch the agent in the SAME session after it exited | YES — natural, deterministic |
| `SessionEnded(SESSION_FINISHED)` | `exit` / `exit N` closes the session (waitpid-proven) | YES — natural, deterministic |
| `SessionEnded(SESSION_REMOVED)` | close the session's tab | YES — natural, deterministic |
| `RuntimeUnknown` (mid-flight RUNNING→UNKNOWN) | needs a failed `/proc` scan (`snapshot == null`) or a previously-matched pid alive-but-unmatched (argv-shape ambiguity) | **NO** — not deterministically producible on hardware without fabricating evidence (forbidden) |

**Q2. Which transitions already have notification mappings?** ALL of them.
The pure `AgentRuntimeNotificationMapping.reduce` covers the complete
vocabulary: `Launched → None`; `ConfirmedRunning → ShowRuntime("<Name> is
running")` with dedup; `RuntimeUnknown → ShowRuntime("<Name> runtime
unknown")` gated on `everPosted` with dedup; `NoLongerDetected → Cancel`
(when a surface exists); `SessionEnded → tombstone` + `ShowExitFact` (the
factual exit statement, gated on `everPosted` + waitpid-proven status) /
`Cancel` (surface outlives session) / `None`. Nothing was missing; nothing
was rewritten.

**Q3. Which mappings are implemented but untested on hardware?** The
in-place UPDATE arms and the unknown-surface arms: the visible
RUNNING→UNKNOWN→RUNNING same-id update cycle, UNKNOWN→NOT_RUNNING
cancellation, and UNKNOWN→SESSION_FINISHED exit-fact replacement. The §53/§54
gates proved the running surface, its tap routing, and multi-session
isolation; the transition-cycle behavior was JVM-pinned only. §55 now gates
the naturally reproducible subset on hardware and honestly marks the rest.

**Q4. Does P6 require implementation changes?** NO. The state machine,
notification identity, cancellation, dedup, tombstones, and the P5 routing
all already implement the mandated behavior. The audit found no defect in
state-transition mapping, notification identity, stale cleanup, update
behavior, or the session-ended transition. **Option A applies** — no
production change is manufactured just to make the phase look productive.

**Q5. The smallest legitimate implementation delta.** One new pure test
class pinning the continuous device story (see §6), TESTING §55, and the
documentation set. Nothing else.

## 4. The device-visible state flow (verified, not redesigned)

```text
ConfirmedRunning      →  "<Name> is running"            (ongoing surface, id = base + sessionId)
    ↓ RuntimeUnknown
"<Name> runtime unknown"   same id, IN-PLACE update, uncertainty-only wording
    ↓ ConfirmedRunning (real evidence returns)
"<Name> is running"        same id, IN-PLACE update, no duplicate storm
    ↓ NoLongerDetected
CANCEL                     same id withdrawn; NO replacement surface
    ↓ (reappearance in-session)
"<Name> is running"        same id re-posted on real evidence
    ↓ SessionEnded (ever-announced session)
"Session ended / Terminal session N exited (code X) / …terminated by signal Y"
                           one-shot factual statement on the same id
```

Every wording is the P4 byte-frozen truth contract. `NoLongerDetected`
never becomes completed/success/finished. Exit code 0 is never success.
`UNKNOWN` is never re-worded as any state claim.

## 5. Notification identity across transitions

One runtime/session → ONE notification id for its whole story:
`NotificationIds.agentRuntime(sessionId) = AGENT_RUNTIME_BASE(20_000) + sessionId`,
deterministic, shared by the running surface, the unknown surface, the
exit fact, and the cancellation. The running→unknown→running cycle is a
state UPDATE on that id (`NotificationManager.notify(id, …)` with
`setOnlyAlertOnce(true)` — no re-alert, no spam); `NoLongerDetected`
cancels exactly that id; the P5 tap route (request code = the
notification id; the route carries only the authoritative session id)
remains correct after every state update because the id and the carried
session id never change. Pinned in P6 by
`AgentRuntimeNotificationTransitionMatrixTest.assertOneIdentity` over
every story fold.

## 6. The P6 test matrix (new coverage — 11 tests/variant)

New file `app/src/test/java/app/pocketshell/notifications/AgentRuntimeNotificationTransitionMatrixTest.kt`
(pure JVM, fold-based over `AgentRuntimeNotificationMapping.reduce`):

1. RUNNING→UNKNOWN updates in place on the same identity; uncertainty-only
   wording (bans "stopped"/"not running" re-wording too).
2. UNKNOWN→RUNNING restores the running surface on the same identity.
3. The RUNNING→UNKNOWN→RUNNING cycle = ONE notification, two in-place
   updates, no cancellation, no second identity.
4. RUNNING→NOT_RUNNING cancels the identity; no replacement surface.
5. **UNKNOWN→NOT_RUNNING cancels too** (the arm P4 pinned only from the
   RUNNING side) — uncertainty withdraws without an absence claim.
6. **UNKNOWN at session end** replaces the surface with the factual exit
   statement (the unknown surface was announced; `everPosted` gates it).
7. UNKNOWN at a SIGNAL-killed session end states the signal,
   session-scoped.
8. Duplicate-delivery storm: repeated identical events around real
   transitions produce exactly one surface per real state (the defensive
   layer over P3c's own dedup).
9. Runtime flapping (R→U→R→U→R) never accumulates notifications — every
   update lands on the one identity, no tombstone.
10. The §55 device story folded end-to-end (spawn → run → withdrawal →
    reappearance → `exit 3`) keeps one identity and honest words.
11. Exit code 0 through the story is never worded success/completion.

Existing coverage that already pinned the rest and remains green:
`AgentRuntimeNotificationMappingTest` (23 — per-arm matrix + tombstone +
honesty sweep), `AgentRuntimeEventsTest` (the P3c engine dedup matrix incl.
the reappearance arm), `AgentRuntimeNotificationRoutingTest` (P5 tap
regression), `AgentRuntimeNotificationInteractionIntegrationTest` (the
structural freezes).

## 7. Device reproducibility — the honest statement (§55 feeds on this)

- **Naturally reproducible (gated in §55):** running appearance, tap
  routing (§54 regression), RUNNING→NOT_RUNNING withdrawal, in-session
  reappearance (NOT_RUNNING→RUNNING), session-end facts (`exit`, `exit 3`,
  tab-close), FGS stability.
- **NOT DEVICE-REPRODUCIBLE IN P6: the mid-flight notification-level
  UNKNOWN transitions** (a *visible* unknown surface updating to running,
  or a running surface degrading to a visible unknown). Triggering one
  requires either a failed procfs scan (transient I/O failure — not
  deterministically producible) or a previously-matched pid that stays
  alive but stops matching (argv-shape mutation — not deterministically
  producible for the supported agents). Fabricating either on hardware
  would require fake injection into production paths, which P6 forbids.
  These arms stay JVM-pinned (tests 1–3, 5–7, 9 above) and are documented
  here and in §55 as exactly that. The birth-UNKNOWN arm (before the
  first scan) IS observable and is gated: it must stay SILENT (no
  uncontextualized uncertainty notification at session birth).

## 8. What P6 proves and does NOT prove

**Proves:** the full transition matrix is implemented coherently at every
layer (engine → mapping → coordinator identity); the device-visible story
keeps ONE notification identity with in-place updates and no spam; the
withdrawal and session-end arms cancel or state facts only; the P5 tap
flow is regression-protected; exit 0 ≠ success holds through every fold;
the naturally reproducible transitions have a written hardware gate.

**Does NOT prove (unchanged from P4/P5):** agent completion, success,
failure, task progress, or waiting-for-input — no such evidence exists in
the architecture, and P6 adds none. A mid-flight unknown→running cycle
observed on real hardware remains future work until a phase legitimizes a
reproduction path.
